# 10 · 平衡調參

> 涵蓋：所有數值旋鈕在哪、怎麼驗證改動、目前的基準數據
> 相關：[03 經濟與抽獎](03-economy.md)（先讀懂公式再來調）

## 旋鈕總覽 · 「我想改 X 要動哪裡」

| 想達成的效果 | 動這裡 | 副作用 |
|---|---|---|
| 整體賺錢速度變快／慢 | `data.js` 各魚的 `value` | 等比縮放，最單純 |
| 拋竿門檻變高／低 | `LOCATIONS[].castCost` | 直接改變倍率分母 |
| 某階級更常出現 | `FG.RARITY[x].weight` | **會稀釋其他所有階級** |
| 裝備加成的天花板 | `RODS[].rareMul`、`EQUIPS[].effect` | 影響後期倍率 |
| 單一釣點的產出 | 該釣點**專屬裝備**的 `effect`（`effect.loc`） | **只影響那一個釣點**，這是調單點最安全的旋鈕 |
| 魚王稀有度 | `RODS[].kingMul`、`BAITS[].kingMul`、`RARITY.king.weight` | 只影響魚王 |
| 高階裝備的邊際效益 | `state.js › rarityTable()` 的指數 `0.85` / `0.70` | 影響 epic/legend 對裝備的敏感度 |
| 大魚出現頻率 | `rollCatch()` 的 `FG.skewed(2.4)` | 數字越大越偏小魚 |
| 大魚的價值溢價 | `rollCatch()` 的 `Math.pow(len/avg, 2.0)` | 指數越大，大物越值錢 |
| 閃光機率／倍率 | `rollCatch()` 的 `0.03` 與 `*= 3` | 純變異度，不影響期望值太多 |
| 魚缸／裝飾價格 | `TANK_LEVELS[].price`、`DECOS[].price` | 籌碼的消耗池。**釣點解鎖已不再是消耗池**，十六個釣點都免費 |
| 每日收入 | `FG.SIGNIN`、`FG.MISSIONS[].reward` | 保底收入，影響新手體驗 |

## 設計目標

| 指標 | 目標值 | 理由 |
|---|---|---|
| 新手產出/成本 | **×1.2 左右** | 穩定前進但感覺得到成本壓力，才有博弈的緊張感 |
| 後期產出/成本 | **×2.0 上下**（滿裝上限 ×2.55） | 升級要有回報，但不能變成印鈔機。上限見 [§為什麼後段釣點的滿裝倍率比較高](#為什麼後段釣點的滿裝倍率比較高) |
| **各釣點滿裝倍率** | **必須單調遞增** | 後面的釣點比前面好賺，是進程的說服力來源。這條比「落在某個區間」更重要 |
| 魚王機率成長 | **0.2% → 0.9%（約 4～5 倍）** | 感覺得到裝備差異，又維持稀有感 |
| 單場自動 50 局 | 淨損益應該**大多為正、偶爾為負** | 有變異才有賭性 |

**倍率不是重點，魚王與圖鑑才是。** 如果調到後期倍率很高，玩家就沒有理由繼續追魚王了。魚王秘餌刻意設計成「貴到把倍率吃掉」，用它是為了機率翻倍，不是為了賺錢。

## 模擬腳本

改完數值**一定要跑這個驗證**。在遊戲頁面的 console 貼上執行（會暫時改動存檔中的裝備，最後會還原）：

```js
(function(){
  function sim(label, rod, baitId, equips, locId){
    const bak = { rod: FG.state.data.rod, bait: FG.state.data.bait, eq: FG.state.data.equips };
    FG.state.data.rod = rod; FG.state.data.bait = baitId; FG.state.data.equips = equips;
    const loc = FG.locById(locId || 'mist_lake');
    const n = 30000; let sum = 0; const cnt = {};
    for (let i = 0; i < n; i++) { const c = FG.state.rollCatch(loc); sum += c.value; cnt[c.rarity] = (cnt[c.rarity]||0)+1; }
    const bait = FG.findById(FG.BAITS, baitId);
    const cost = FG.state.castCost(loc) + bait.price;
    const d = {}; for (const k in cnt) d[k] = (cnt[k]/n*100).toFixed(2);
    Object.assign(FG.state.data, { rod: bak.rod, bait: bak.bait, equips: bak.eq });
    return label + ' | EV=' + Math.round(sum/n) + ' 成本=' + cost +
      ' 倍率=' + (sum/n/cost).toFixed(2) +
      ' | king=' + (d.king||0) + '% legend=' + (d.legend||0) +
      '% epic=' + (d.epic||0) + '% rare=' + (d.rare||0) + '%';
  }
  const FULL = ['eq_hat','eq_vest','eq_basket','eq_clover','eq_sonar'];
  const MID  = ['eq_hat','eq_vest','eq_basket','eq_clover'];
  const r = [];
  r.push(sim('新手  ', 'rod_bamboo',  'bait_bread',  []));
  r.push(sim('中期  ', 'rod_carbon',  'bait_shrimp', ['eq_hat','eq_basket']));
  r.push(sim('後期  ', 'rod_mithril', 'bait_lure',   MID));
  r.push(sim('滿裝  ', 'rod_dragon',  'bait_king',   FULL));
  // 「舊頂裝」逐一掃過所有釣點：這一組要維持單調遞增
  FG.LOCATIONS.forEach(function (l) {
    r.push(sim('舊頂·' + l.name, 'rod_dragon', 'bait_king', FULL, l.id));
  });
  // 中段配置（形成裝備門檻，**不要求**單調）
  ['rapids', 'coral_reef', 'sakura_shrine', 'tide_flat', 'frost_lake', 'fall_pool', 'lotus_river', 'caldera', 'abyss', 'world_root', 'cavern', 'dawn_port']
    .forEach(function (id) { r.push(sim('中段·' + FG.locById(id).name, 'rod_mithril', 'bait_lure', MID, id)); });
  // 新頂裝：要把該釣點的「專屬裝備」也帶上，否則量到的不是實際上限
  FG.LOCATIONS.forEach(function (l) {
    const own = FG.EQUIPS.filter(function (e) { return e.effect && e.effect.loc === l.id; }).map(function (e) { return e.id; });
    r.push(sim('頂裝·' + l.name, 'rod_sceptre', 'bait_scarab', FULL.concat(own), l.id));
  });
  FG.state.save();
  console.log(r.join('\n'));
})()
```

**注意**：`sim()` 的成本只算「拋竿費 + 一份餌料」，沒有計入家園裝飾的 `valueMul`（因為模擬時讀的是玩家當下的存檔）。要比較純裝備效果，先確保存檔沒買裝飾，或在腳本開頭加一行 `FG.state.data.deco = {};`（上面的基準表就是這樣跑的）。

### 精確版：不用模擬，直接把期望值算出來

**`rollCatch()` 的每一項都是可積的，所以期望值有解析解。** 一旦釣點多到要「插隊」，這件事就從加分變成必要——見下方 §窗口。

推導：`t' = clamp(U^2.4 · (1+sizeBonus) + sizeBonus·0.25, 0, 1)`，`len = min + (max−min)·t'`，而

```
E[value] = fish.value / avg² · ( min² + 2·min·range·E[t'] + range²·E[t'²] )
           × (雜物 ? 1 : valueMul · bait.valueMul · 1.06)
```

`1.06` 是閃光的期望倍率（`0.97·1 + 0.03·3`，雜物不吃閃光）。`E[t']` 與 `E[t'²]` 對 `u` 做 20 萬點的中點積分就好，誤差約 1e-10。階級機率直接取 `rarityTable()` 的 `weight/total`，階級內是等機率，所以

```
EV = Σ_階級 P(階級) × (該階所有魚的 E[value] 平均)
```

**跟模擬的關係**：兩者算的是同一個東西，實測 100 萬竿的模擬與解析解差在小數第二位（例如深淵滿裝 2.49 vs 2.507）。**解析解用來調參，模擬用來交叉驗證公式有沒有抄錯**——兩份公式都可能寫錯，但不太可能錯得一模一樣。

> 腳本放在暫存目錄不進版控（它跟 `state.js` 的公式是兩份，留在 repo 裡遲早會失同步）。要用的時候照上面的式子重寫一份，二十行內寫得完。

### 窗口：插隊比接尾難，而且會越來越難

滿裝倍率必須單調遞增，而那條曲線是**收斂**的（見下方基準表）。所以在既有兩個釣點之間插一個新的，可用的區間就是「前一站的倍率」到「後一站的倍率」之間——而那個區間已經很窄了：

| 插在哪 | 可用窗口 | 寬度 |
|---|---|---|
| 晨霧湖 → 落霞峽灣 | (1.908, 2.256) | 0.348 |
| **澄澈方池 → 落霞峽灣** | (2.082, 2.256) | 0.174 |
| **落霞峽灣 → 宵櫻神域** | (2.256, 2.389) | 0.133 |
| 宵櫻神域 → 幽藍冰湖 | (2.389, 2.407) | **0.018** |
| 幽藍冰湖 → 煙雨蓮江 | (2.407, 2.461) | 0.054 |
| 煙雨蓮江 → 深淵海溝 | (2.461, 2.507) | 0.046 |

**0.018 的窗口比 100 萬竿模擬的噪音（±0.025）還窄。** 這就是為什麼上面那節存在：用模擬去瞄準這種窗口，等於在追雜訊。

> **但前段還很鬆，而且鬆得多。** 2026-08-05 插進去的兩個釣點用掉的是 0.174 與 0.133 這兩個窗口——比後段寬一個數量級，用模擬瞄準都綽綽有餘（實測 40 萬竿的模擬與解析解只差在小數第三位）。**要插隊就往前段插。** 2,300 以後那幾段最窄剩 0.009，實務上已經插不下了。

實際做法：先把新釣點的 `value` 用 §加新釣點的抓法 填一版，用解析解量出目前的倍率，再算出「落到窗口正中央」需要的縮放係數，把**所有非雜物 `value`** 整批乘上去。六個插隊釣點用的係數是 **澄澈方池 ×1.173、亂石急湍 ×1.0574、琉璃珊瑚 ×1.0674、潮落礁灘 ×1.0672、懸瀑深潭 ×1.0406、硫煙湯湖 ×1.0057**。

> **雜物的 `value` 不跟著縮放。** 它不吃 `valueMul`、不吃閃光，對 EV 的貢獻只有百分之幾，縮放它只會讓數字變醜。這跟煙雨蓮江當初「整批乘 0.965」的做法一致。

### 不進遊戲也能跑（離線版）

`data.js` 是純資料、沒有 DOM 依賴，可以在 Node 裡直接載入，把 `bonus()` / `rarityTable()` / `rollCatch()` 複刻一份來跑大樣本（30 萬竿只要幾秒）。做法：

```js
global.window = {};
new Function(require('fs').readFileSync('js/data.js', 'utf8'))();
const FG = global.window.FG;   // 之後照 state.js 的公式重寫三個函式即可
```

**代價是公式有兩份，改了 `state.js` 就必須同步改離線腳本，否則基準表會騙人。** 跑完務必用遊戲內的版本抽驗一次。

## 兩種「頂裝」，兩張基準表

自從每個釣點都有專屬周邊之後，「滿裝」有兩個意思，**兩個都要記**：

| 配置 | 內容 | 用來看什麼 |
|---|---|---|
| **舊頂裝** | 龍骨釣竿 ＋ 魚王秘餌 ＋ 五件通用裝備 | **歷史可比性**。這組配置從專案早期就存在，數字沒變過，所以它是唯一能拿來跟舊紀錄對照的基準 |
| **新頂裝** | 黃金權杖竿 ＋ 聖甲蟲餌 ＋ 五件通用 ＋ **該釣點的專屬裝備** | **現在的實際上限**。玩家真的全買齊之後就是這個 |

兩組都必須維持**單調遞增**。新頂裝在便宜釣點反而更低（聖甲蟲餌一份 2,600，在晨霧湖佔成本 86%），這是**正確的行為**——沒有人會帶頂級餌去晨霧湖。

> ⚠️ **「新頂裝」是一組固定的配置（黃金權杖竿＋聖甲蟲餌），不是「當下最好的裝備」。** 2026-08-06 之後最好的竿與餌已經是吊桿改造竿（2,800,000）與白布假餌（5,000），那一組量出來是 0.486 → 0.613 → … → 2.768 → **2.866**（同樣嚴格遞增，曉日沉港最高）。**這張表刻意不換配置**——換了就失去跟舊紀錄對照的能力，而那正是保留兩張表的理由。要看真正的上限就照上面那串數字。另外用遊戲內的蒙地卡羅跑 40 萬竿交叉驗證，量到 澄澈方池 2.082 ／ 亂石急湍 2.169 ／ 落霞峽灣 2.258 ／ 琉璃珊瑚 2.325 ／ 宵櫻神域 2.377 ／ 黃沙冥河 2.585 ／ 鐘乳暗穴 2.636，同樣遞增。

> **鐘乳暗穴的 ×2.619 沒有經過校正**，是直接照 §加新釣點的抓法 的 ≈48,000 那一欄填出來就落在窗口裡的。這印證了那一欄「已經收斂、可以直接沿用」的判斷——**接在尾巴的釣點現在幾乎不用調參**，難的全部集中在插隊。

新頂裝在前十一個釣點比舊頂裝低（只有黃沙冥河反超），是因為餌價從 900 漲到 2,600——**這是設計，不是失衡**：頂級餌只在頂級釣點划算。

「中段」那一欄**不要求單調**：它從晨霧湖的 ×2.02 一路掉到後段的 ×1.6，就是[§為什麼後段釣點的滿裝倍率比較高](#為什麼後段釣點的滿裝倍率比較高)最後一段講的裝備門檻——新釣點不是解鎖了就該去，是備齊裝備才該去。

> **改了任何數值，重跑模擬並更新這兩張表。** 這是這頁存在的意義——沒有更新的基準表比沒有表更糟。

> ⚠️ **滿裝倍率的模擬噪音比想像中大。** 期望值被魚王那一項主宰（機率 0.9%、價值數十萬），30 萬竿只抽到約 2,700 條魚王，倍率的抖動就有 ±2%。**要判斷「這個釣點是不是真的比隔壁高」必須跑 100 萬竿以上，並且跑兩次看重現性。** 用 30 萬竿的數字去微調 `value` 會追著噪音跑。

### 為什麼後段釣點的滿裝倍率比較高

晨霧湖滿裝只有 ×1.90，深淵滿裝卻有 ×2.51——不是失衡，是**餌料成本佔比造成的**：魚王秘餌固定 900／份，在晨霧湖佔總成本 73%，在深淵只佔 8%。所以同一套裝備，越深的釣點分母被餌料稀釋得越少，倍率自然往上。

這個效果被**刻意保留**，因為它剛好構成一條**收斂**的進程曲線：

| 釣點 | castCost | 滿裝倍率 | 相對前一站 |
|---|---|---|---|
| 晨霧湖 | 400 | ×1.908 | — |
| 澄澈方池 | 700 | ×2.082 | +0.174 |
| 亂石急湍 | 900 | ×2.169 | +0.087 |
| 落霞峽灣 | 1,100 | ×2.256 | +0.087 |
| 琉璃珊瑚 | 1,400 | ×2.323 | +0.067 |
| 宵櫻神域 | 1,800 | ×2.389 | +0.066 |
| 潮落礁灘 | 2,300 | ×2.398 | +0.009 |
| 幽藍冰湖 | 3,000 | ×2.407 | +0.009 |
| 懸瀑深潭 | 4,400 | ×2.434 | +0.027 |
| 煙雨蓮江 | 6,000 | ×2.461 | +0.027 |
| 硫煙湯湖 | 9,000 | ×2.484 | +0.023 |
| 深淵海溝 | 12,000 | ×2.507 | +0.023 |
| 世界樹根 | 24,000 | ×2.539 | +0.032 |
| 黃沙冥河 | 48,000 | ×2.600 | +0.061 |
| 鐘乳暗穴 | 96,000 | ×2.619 | +0.019 |
| 曉日沉港 | 192,000 | ×2.642 | +0.023 |

增量一路收斂（+0.17 → 約 +0.02），**倍率的漸近值大約在 ×2.65**（曉日沉港的 ×2.642 已經貼到那條線了），因為餌料佔比已經稀釋到接近零、分母幾乎只剩拋竿費。這是好事：越深的釣點確實比較好賺，但差距只有四成，不會讓前面的釣點變成完全沒理由待。真正的落差在**絕對值**（曉日沉港一竿的 EV 是晨霧湖的 183 倍），玩家追的是那個。

> **插隊的釣點會把增量切成兩半。** 上表中好幾對的數字一樣（方池/急湍 +0.087、峽灣/珊瑚 +0.067、礁灘/冰湖 +0.009、深潭/蓮江 +0.027、湯湖/深淵 +0.023），因為新釣點刻意放在原本那一段的**正中央**——這是 [§窗口](#窗口插隊比接尾難而且會越來越難) 的做法造成的必然結果。**代價是每插一個，那一段剩下的窗口就再對半砍一次。**
>
> **所以前段跟後段的難度差了一個數量級。** 400～1,800 那幾段還有 0.067～0.087 可用，再插一輪都沒問題；2,300 之後最窄剩 0.009，實務上插不下了。**接在最後面永遠是最寬鬆的**（現在是 2.619 → 漸近線 2.65+），而且照係數表填一次就會中，不用校正。

**這條曲線必須維持單調遞增，這是唯一真正要驗的事。** 煙雨蓮江初次填魚時跑出 ×2.55，比當時後面的深淵還高——玩家會發現「前一個釣點反而比較好賺」，整條進程的說服力就沒了。修正方式是把所有非雜物 `value` 整批乘 **0.965**，落回 ×2.45。

> 上面那條「1.9～2.5」的設計目標**已經跟著世界樹根上修成 1.9～2.55**。這不是放寬標準，是承認漸近線的位置：castCost 拉到 24,000 之後，就算 `value` 係數壓到最低，倍率也不可能回到 2.5 以下而不破壞單調遞增。**再往後加釣點時，倍率只會更貼近 2.55，不會突破。**

同一組數字的另一面：後段釣點用「秘銀竿＋假餌」只有 ×1.6～1.7，明顯比晨霧湖的 ×2.02 差。這是有意的門檻——**新釣點不是解鎖了就該去，是備齊裝備才該去。**

## 調參歷史與教訓

### 稀有度倍率的疊乘失控（已修正）

初版：`rare` 以上全部乘 `M`，`king` 再額外乘 `K`。
問題：滿裝時 `M ≈ 4.7`、`K ≈ 6`，`king` 權重被放大 **70 倍**，機率飆到 6.8%。魚王變成常態，追逐感消失。
修正：改成 epic `M^0.85`、legend `M^0.70`、**king 只吃 K 完全不吃 M**，同時把 `rod_dragon` 的 rareMul 2.2→1.8、kingMul 2.5→2.0，`bait_king` 的 rareMul 2.3→1.9、kingMul 4→3。
教訓：**多個 1.2～2.5 的倍率連乘會爆炸**。任何新增的加成來源都要重跑模擬。

### 初版產出過高（已修正）

初版魚的 `value` 偏高、`castCost` 偏低，新手倍率高達 ×6。修正方式是同時降 `value`、升 `castCost` 到 400。
教訓：**先定 `castCost`，再回推 `value`**，比反過來好調。

### 魚王秘餌定價（已修正）

初版 1,800/份，導致滿裝倍率只有 ×1.03，玩家用它純虧。降到 900 後倍率回到 ×1.92，同時保留「比後期配置更貴、換取魚王機率翻倍」的取捨。

### 一釣點一件專屬裝備，是為了不再重演疊乘失控

每個釣點都要有專屬裝備（[09 §新增一個釣點](09-recipes.md#新增一個釣點--一次要生出一整套)）。**如果那八件是通用裝備，就會直接重演上面那次事故**——裝備效果全部同時生效且相乘，八件各 1.15 就是 ×3.06 疊在 `M` 上面。

解法是 `effect.loc`：專屬裝備只在它的釣點生效（`state.js › bonus(loc)` 直接 `continue` 跳過）。**同一時間只有一件，加到第一百件也只多一個乘數。**

初版還踩了第二層：**每件專屬裝備給了 `rareMul` + `valueMul` 兩個效果**，結果黃沙冥河跑出 **×3.13**（跟下面那次 ×3.25 是同一個量級的印鈔機）。改成一件只給一個效果之後回到 ×2.69。

**教訓**：一件裝備兩個乘數，效果不是 1+1，是把兩條不同的放大路徑（權重 × 售價）同時打開。**一件一個效果**，順便也讓每件裝備有自己的個性。

### 帶頂級竿回頭刷新手池：是既有現象，不是漏洞

用最好的竿子配**便宜的餌**去晨霧湖，倍率是 **×3.19**（比任何釣點的頂裝都高）。這件事在加新竿之前就存在（龍骨竿＋活蝦 = ×3.01），新竿只把它從 3.01 推到 3.19。

**不需要修**，因為倍率高但**絕對值極小**：

| | 倍率 | EV／竿 | 淨賺／竿 |
|---|---|---|---|
| 權杖竿＋活蝦 @晨霧湖 | ×3.19 | 1,720 | 約 1,180 |
| 權杖竿＋聖甲蟲餌 @黃沙冥河 | ×2.69 | 114,940 | 約 71,500 |

差 60 倍。**這正是「真正的落差在絕對值」那條設計原則在生效**——玩家不會為了漂亮的倍率放棄 60 倍的收入。加新釣點時只要確認這個關係還成立（絕對值差距 ≫ 倍率差距）就不用管倍率的排名。

### 高 castCost 釣點的 value 係數要往下調（已修正）

幽藍冰湖與深淵海溝初次填魚時，直接套用當時「common ≈ castCost × 0.25、good ≈ ×0.5、rare ≈ ×2 …」的抓法，跑出來滿裝倍率是 **×3.25 / ×3.97**，等於印鈔機。

原因是那組係數是照晨霧湖／落霞峽灣回推的，而那兩個釣點的成本裡有很大一塊是**固定 900 的魚王秘餌**。castCost 一路拉到 3,000／12,000 之後，餌料佔比從七成掉到不到一成，分母幾乎只剩拋竿費，倍率就整條往上平移。

修正方式是把兩個釣點的所有 `value` 整批乘上 **0.74（冰湖）／0.63（深淵）**，讓滿裝倍率落回 ×2.40 / ×2.51。

教訓：**value/castCost 的係數不是常數，會隨 castCost 增加而遞減。** 不要套用固定倍數就交差，一定要跑模擬。

## 加新釣點的抓法

1. 先定 `castCost`。
2. 各階級的 `value` 用下表抓初值——**係數隨 castCost 遞減**，原因見上一節：

   | 稀有度 | ≈ 400～1,100 | ≈ 1,800 | ≈ 3,000 | ≈ 6,000 | ≈ 12,000 | ≈ 24,000 | ≈ 48,000 |
   |---|---|---|---|---|---|---|---|
   | common | ×0.25 | ×0.13 | ×0.10 | ×0.087 | ×0.08 | ×0.075 | ×0.075 |
   | good | ×0.5 | ×0.42 | ×0.34 | ×0.31 | ×0.30 | ×0.29 | ×0.29 |
   | rare | ×2 | ×1.75 | ×1.5 | ×1.35 | ×1.3 | ×1.26 | ×1.26 |
   | epic | ×8 | ×6.8 | ×5.8 | ×5.25 | ×5.1 | ×4.95 | ×4.95 |
   | legend | ×22 | ×19 | ×16 | ×14.5 | ×14 | ×13.6 | ×13.6 |
   | king | ×85 | ×75 | ×65 | ×56 | ×51 | ×47.5 | ×47.5 |

   **≈48,000 那一欄跟 ≈24,000 一樣**，不是懶得算——係數已經收斂了（king 的差分 −9 → −5 → −3.5 → 趨近 0）。黃沙冥河直接照抄 24,000 那一欄就落在 ×2.59，沒有回頭調整。**再往後加釣點大概也可以直接沿用這一欄。**

   > **這個判斷已經連續驗證三次了。** 鐘乳暗穴（96,000）與曉日沉港（192,000）都是直接照抄 ≈48,000 那一欄、一次就落在窗口裡（×2.619 / ×2.642），完全沒有校正。**castCost 超過 48,000 之後，這一欄就是常數**——因為分母幾乎只剩拋竿費，`value/castCost` 的比例固定了，倍率的差別只來自餌價佔比那一點殘餘。

   宵櫻神域就是照 ≈1,800 那一欄直接填出來的，一次就落在 ×2.40，沒有回頭調整。

   **≈6,000 那一欄是煙雨蓮江校正後的實際值，不是內插值。** 內插（log 中點）給出的係數偏高 3.5%，跑出 ×2.55 而不是目標的 ×2.45。**中間欄位不要用內插硬填**——係數對 castCost 的關係不是 log 線性的。新的 castCost 落在兩欄之間時，先取較高那一欄的係數（會偏保守／偏低），再跑模擬往上調。

   **≈24,000 那一欄是世界樹根用「外插」抓出來的，而且一次就中（×2.54）。** 做法是看 3,000 → 6,000 → 12,000 的**差分**再延伸一格（king：65 → 56 → 51，差 −9、−5，所以下一格取 −3.5 ≈ 47.5）。**外插比內插可靠**，因為係數的變化率本身在收斂。

   **castCost 落在兩欄之間時（= 插隊），別想用這張表一次到位。** 四個新釣點的 castCost（700 / 2,300 / 4,400 / 9,000）都不在欄位上，做法是「先取**較高**那一欄的係數（偏保守、會落低），再用[解析解](#精確版不用模擬直接把期望值算出來)反推縮放係數補上去」：

   | 釣點 | castCost | 初值用哪一欄 | 落點 | 校正係數 | 校正後 |
   |---|---|---|---|---|---|
   | 澄澈方池 | 700 | ≈400～1,100 | ×1.775 | ×1.173 | ×2.082 |
   | 亂石急湍 | 900 | ≈400～1,100 | ×2.051 | ×1.0574 | ×2.169 |
   | 琉璃珊瑚 | 1,400 | ≈1,800 | ×2.176 | ×1.0674 | ×2.323 |
   | 潮落礁灘 | 2,300 | ≈3,000 | ×2.247 | ×1.0672 | ×2.398 |
   | 懸瀑深潭 | 4,400 | ≈6,000 | ×2.339 | ×1.0406 | ×2.434 |
   | 硫煙湯湖 | 9,000 | ≈12,000 | ×2.470 | ×1.0057 | ×2.484 |

   六個都偏低（符合「取較高那一欄會偏保守」的預期），而且**castCost 越大偏得越少**——係數表在後段已經幾乎是平的，所以 9,000 那個只差 0.6%。**插在前段的釣點才需要認真校正。**

   **接在尾巴的則完全不用校正。** 鐘乳暗穴（96,000）與曉日沉港（192,000）都是直接照抄 ≈48,000 那一欄就落在 ×2.619 / ×2.642，跟黃沙冥河當初一樣一次就中。這一欄看來可以無限沿用下去。

3. 選一種**沒有人用過的 `scene.terrain`**（見 [06 §地形系統](06-pixel-engine.md#三之二--地形系統--terrain)），`unlock` 填 `{ free: true }`——**現行設計是進程門檻全部由 `castCost` 承擔**，不收解鎖費（理由見 [07](07-data-schema.md#為什麼所有釣點都是免費的)）。真要收費才用 `{ chips: N }`，抓 `castCost × 100～130`。
4. 魚種配額照 [07 §一個釣點該放幾條魚](07-data-schema.md#一個釣點該放幾條魚)，**每一階都要有魚**——缺席的階級權重會直接消失，剩下的階級被放大。
5. 跑模擬。目標：滿裝倍率 1.9～2.5、「秘銀竿＋假餌」的中段配置明顯偏低（形成裝備門檻）。
6. 只要動了 `value`，**回來更新上面的基準表**。
