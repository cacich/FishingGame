# 10 · 平衡調參

> 涵蓋：所有數值旋鈕在哪、怎麼驗證改動、目前的基準數據

## 最重要的一句話

**你不可能靠改數值改變 RTP。** `state.js › rtpNorm()` 每次抽獎前都會把期望值重新歸一到 `bet × 0.98`（原理見 [03 §七](03-economy.md#七--固定-rtp-的核心--rtpnormloc-rows-boost)）。改 `fish.mult`、改裝備倍率、改稀有度權重——全部只會改變**分布形狀**，總期望值紋風不動。

要改 RTP 只有一個地方：`data.js › FG.RTP_TARGET`。

## 旋鈕總覽 · 「我想改 X 要動哪裡」

| 想達成的效果 | 動這裡 | 副作用 |
|---|---|---|
| **改 RTP 本身** | `data.js › FG.RTP_TARGET` | 唯一能動 RTP 的地方。改完不用做別的，恆等式會自己成立 |
| 大獎更大／平時更乾 | 換算腳本的波動度曲線（見下節），重跑 | 純波動度，RTP 不變 |
| 某階級更常出現 | `FG.RARITY[x].weight` | **會稀釋其他所有階級**；`rtpNorm` 會把賠付等比壓回去 |
| 魚王機率 | `RODS[].kingMul`、`EQUIPS[].effect.kingMul`、`RARITY.king.weight` | 影響圖鑑進度與 jackpot 頻率 |
| 大獎倍率 | `BAITS[].jackpotMul`、`EQUIPS[].effect.jackpotMul` | 傳說／魚王的賠付上升，其餘被 `rtpNorm` 壓低 |
| 下注階梯 | `data.js › FG.BETS` | 選項數量會影響 UI（`.seg-scroll` 撐得住，見 [08](08-ui-and-screens.md)） |
| 進程門檻 | `LOCATIONS[].minBet` | 決定該釣點的最低注與可選檔數 |
| 大魚出現頻率 | `rollCatch()` 的 `FG.skewed(2.4)` | 數字越大越偏小魚。**不影響 EV**（`rtpNorm` 吸收） |
| 大魚的賠付溢價 | `rollCatch()` 的 `Math.pow(len/avg, 2.0)` | 指數越大，大物賠越多。**不影響 EV**，只影響波動 |
| 閃光機率／倍率 | `rollCatch()` 的 `0.03` 與 `*= 3` | ⚠️ 改了要同步改 `state.js › SHINY_EV`（目前 1.06），否則 `rtpNorm` 會算錯 |
| Buffer 回吐速度 | `state.js › BUFFER_BOOST_MAX` / `BUFFER_DRAIN` | 只影響「什麼時候拿到」，不影響總量 |
| 商店價格 | `RODS/BAITS/EQUIPS/DECOS/TANK_LEVELS[].price` | **不影響 RTP**（錢會進 Buffer 池回吐），只影響現金流節奏 |
| 每日收入 | `FG.SIGNIN`、`FG.MISSIONS[].reward` | 行銷成本，不列入 RTP 分母 |

## 設計目標

| 指標 | 目標值 | 理由 |
|---|---|---|
| **總體 RTP** | **98%（恆定）** | 產品需求。定義與兩種口徑見 [03 §一](03-economy.md#一--兩種-rtp-口徑先對齊定義其他都建立在這上面) |
| 各釣點波動度 | **單調遞增** | 深釣點沒有「比較好賺」可言（RTP 一樣），進程感只能來自「賭得比較大」 |
| 魚王機率成長 | 0.20% → 約 0.58%（約 2.9 倍） | 感覺得到裝備差異，又維持稀有感 |
| 新手回本率 | 約 40% | 無裝備時優良階賠付要略高於 1×，否則開局體感太差 |
| 單件裝備幅度 | **+2%～+5%** | 六件同時相乘約 ×1.20，每一件的貢獻玩家看得懂 |
| 單支竿／單種餌幅度 | 可以大（竿 →×2.5、餌 →×1.6） | 同時只有一件生效，不會疊乘 |

**倍率不是重點，魚王與圖鑑才是。** 這句話在舊版就成立，改成固定 RTP 之後只是變得更絕對——現在**不存在**「哪個配置比較賺」這件事。

## 波動度曲線（唯一真正要調的東西）

魚的 `mult`（相對 bet 的賠付倍率）不是手填的，是用換算腳本從一條曲線生出來的。曲線定義在腳本裡，`v = 釣點索引 / 15`（0 = 晨霧湖，1 = 曉日沉港）：

| 階級 | 基礎機率 | v=0（晨霧湖） | v=1（曉日沉港） |
|---|---|---|---|
| junk | 9.0% | 0.05 | 0.02 |
| common | 52.0% | 0.55 | 0.20 |
| good | 26.0% | 0.95 | 0.45 |
| rare | 9.0% | 2.20 | 1.50 |
| epic | 3.0% | 6.00 | 6.00 |
| legend | 0.8% | 15.0 | 30.0 |
| king | 0.2% | 40.0 | 170.0 |

線性內插，然後**每個釣點整批縮放**，讓「無裝備基礎配置」下的 EV 剛好落在 0.98——這樣 `rtpNorm` 在基礎配置下 ≈ 1.000（實測 1.0001），`mult` 的數字就是玩家實際會看到的倍率。各釣點的縮放係數落在 1.066～1.100。

> **兩端的 EV 要先湊到差不多再交給縮放。** 初版 v=1 那一欄的 EV 是 v=0 的 1.49 倍，縮放係數變成 1.105 vs 0.743，`mult` 全被壓掉四分之一，公布的倍率數字跟設計意圖對不上。把 common/good/rare 一起壓下來讓兩端 EV 落在 1.116 附近之後，係數才收斂到同一個量級。

### 換算腳本

腳本放在暫存目錄不進版控（它跟 `data.js` 的格式綁在一起，留在 repo 裡遲早會失同步）。要重跑的話，它做四件事：

1. 載入 `data.js` 取得目前的 `mult`（或舊版的 `value`）。
2. 依上表算出每個釣點每個階級的目標倍率。
3. 階級內按現有數值的**相對比例**分配，保留每條魚的個性。
4. 對每個釣點解出縮放係數，讓基礎 EV = `FG.RTP_TARGET`；四捨五入到 3 位有效數字後，逐行替換 `data.js`。

替換是安全的：**每條魚的 `mult` 都跟它的 `id` 在同一行**，所以可以逐行比對 id 再換。腳本會斷言替換筆數 = 370，對不上就中止不寫檔。

## 驗證：驗恆等式，不要驗統計量

**這是本頁最重要的方法論改動。**

舊版靠蒙地卡羅量倍率，而 EV 有 8%～60% 壓在機率 0.2%～0.6% 的魚王身上——200 萬竿也只抽到幾千條，標準誤差 0.5%，分布還右偏（多數樣本低於期望值）。用它去微調數值就是在追雜訊。

現在 RTP 是恆等式，所以直接**窮舉驗證**就好：

```
16 釣點 × 21 竿 × 21 餌 × 3 裝備配置 × 各釣點可用的 bet 檔 = 243,432 組
→ RTP 與 0.980000 的最大誤差 4.441e-16（浮點精度極限）
```

驗證腳本**載入真正的 `util.js` / `data.js` / `state.js`**，呼叫 `state.bonus()` / `rarityTable()` / `rtpNorm()` / `sizeMoments()` / `payoutMult()` 本身，不重寫任何公式——這樣就沒有「公式有兩份會失同步」的問題（那是舊版離線腳本最大的維護成本）。

```js
global.window = {};
global.localStorage = { getItem: () => null, setItem: () => {}, removeItem: () => {} };
global.document = { createElement: () => ({ style: {}, classList: { add(){}, remove(){}, toggle(){} }, appendChild(){} }) };
['util.js','data.js','state.js'].forEach(f => new Function(require('fs').readFileSync('js/'+f,'utf8'))());
const st = global.window.FG.state;
st.data = { /* 手動塞一份乾淨的存檔，不要跑 init() */ };
```

### 蒙地卡羅還是有用，但要拆開用

要交叉驗證公式有沒有抄錯，就拆成兩個**低變異**的量：

| 量 | 為什麼低變異 |
|---|---|
| **非魚王的賠付** | 拿掉那條長尾之後變異小一個數量級 |
| **魚王的出現頻率** | 伯努利，跟賠付大小無關 |

實測 200 萬竿：

| 配置 | 非魚王 EV/bet 模擬 vs 解析 | 魚王率 模擬 vs 解析 |
|---|---|---|
| 晨霧湖 · 無裝備 | 0.9078 vs 0.9054 | 0.200% vs 0.200% |
| 宵櫻神域 · 秘銀竿＋假餌＋通用五件 | 0.6480 vs 0.6514 | 0.428% vs 0.424% |
| 曉日沉港 · 滿裝 | 0.3648 vs 0.3636 | 0.587% vs 0.581% |

### Buffer 池的驗證

同樣是驗恆等式，不是驗統計：

- **(a) 排空量 = 進池量**：每竿扣的是確定值 `bet × boost`，跟賠付的隨機性無關。實測進池 980,000 → 排空 980,000，誤差 5.1e-9，用了 15,711 竿。
- **(b) `boost` 生效時 `EV/bet = 0.98 + boost`**：實測 boost 0 / 0.01 / 0.05 / 0.10 → 0.980000 / 0.990000 / 1.030000 / 1.080000，誤差 1.1e-16。

**不要用「跑到池排空，看實付比基準多多少」來驗。** 那個量的標準誤差被魚王主宰（1.2 萬竿只有約 23 條魚王，每條賠 4 萬），實測會偏離期望值一半以上——看起來像 bug，其實是噪音。

## 調參歷史與教訓

### 為什麼最後做成固定 RTP（2026-08-06）

舊版是「調出來的平衡」：`value` 手填 → 跑模擬 → 看滿裝倍率有沒有單調遞增 → 整批乘一個係數校正。這套方法有三個結構性問題，最後全都爆掉：

1. **可用窗口越調越窄。** 滿裝倍率的曲線是收斂的，插一個新釣點的可用區間從 0.348 一路縮到 **0.009**——比 100 萬竿模擬的噪音（±0.025）還窄。到最後「插隊」實務上做不到了。
2. **加內容就會破壞平衡。** 每加一件通用裝備都把所有釣點的倍率一起推高，出過兩次印鈔機事故（見下）。
3. **公式有兩份。** 離線模擬腳本跟 `state.js` 各一份，改了一邊忘了另一邊，基準表就會騙人。

固定 RTP 把三個問題一次消掉：窗口不存在了（RTP 是恆等式）、加內容不可能破壞平衡（`rtpNorm` 吸收）、驗證腳本直接載入 `state.js` 本體（不可能失同步）。

**代價寫在前面**：竿、餌、裝備全部變成波動度旋鈕之後，「換裝備」不再讓玩家變有錢。進程的驅動力剩下圖鑑收集、魚王 jackpot、解鎖更高的 minBet 檔位。這是 98% 固定 RTP 的必然結果，沒有別的解。

### 稀有度倍率的疊乘失控（舊版事故，已結構性消除）

初版：`rare` 以上全部乘 `M`，`king` 再額外乘 `K`。滿裝時 `M ≈ 4.7`、`K ≈ 6`，`king` 權重被放大 **70 倍**，機率飆到 6.8%。
當時的修正：改成 epic `M^0.85`、legend `M^0.70`、king 只吃 `K`。
**現在的處置**：`M` 整個拿掉了（`rareMul` 已從資料表移除），中間五階的權重固定不動。指數遞減那套補丁也一併消失。

### 一釣點一件專屬裝備的理由變了

舊版 `effect.loc` 是**安全機制**：八件通用裝備各 1.15 就是 ×3.06 疊在 `M` 上面，會直接重演上面那次事故。初版還踩了第二層——每件給了 `rareMul` + `valueMul` 兩個效果，黃沙冥河跑出 **×3.13**。

**現在 `effect.loc` 不再是安全機制**（疊乘失控在固定 RTP 下不可能發生），它純粹是內容規則：一釣點一整套周邊，讓每個釣點保有自己的一件東西。「一件一個效果」也保留了，但理由從「防疊乘」變成「玩家看得懂」。

### 高 castCost 釣點的 value 係數（舊版問題，已不存在）

幽藍冰湖與深淵海溝初次填魚時直接套用固定係數，跑出滿裝 **×3.25 / ×3.97**。原因是那組係數是照淺釣點回推的，而深釣點的餌料成本佔比從七成掉到不到一成，分母幾乎只剩拋竿費。
**現在不存在**：賠付是 bet 的倍率、餌價不進分母（進 Buffer 池），成本結構在所有釣點完全相同。舊版那張「係數隨 castCost 遞減」的表已刪除。

### 帶頂級竿回頭刷新手池（舊版現象，已不存在）

舊版用最好的竿配便宜的餌去晨霧湖，RTP 是 **×3.58**（比任何釣點的頂裝都高），因為餌價佔比被壓到極低。當時的判斷是「不用修，因為絕對值差 330 倍」。
**現在不存在**：所有配置的 RTP 都是 98%，餌價不影響划不划算。連帶「頂級餌只在頂級釣點划算」這條舊結論也一併作廢。

### 餌價在固定 RTP 下不影響划不划算

值得單獨記一筆，因為它反直覺：貴餌花掉的錢有 98% 會從 Buffer 池回來，所以「用貴餌划不划算」這個問題**沒有意義**。餌的意義只剩兩個——大獎倍率（`jackpotMul`）與少釣到雜物（`junkMul`）。餌價現在只影響現金流節奏與 Buffer 池的累積速度。
