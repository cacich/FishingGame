# 03 · 經濟與抽獎

> 涵蓋：`js/state.js › bet() / bonus() / rarityTable() / rtpNorm() / rollCatch() / bufferBoost() / toBuffer() / recordCatch()`、`js/data.js › FG.RARITY / FG.BETS / FG.RTP_TARGET`

這是整個遊戲的心臟。**改這裡之前先讀完整頁**，公式之間有耦合。

> 玩家自選下注額，每一竿的期望回報被**釘死**在 `bet × 98%`。舊版那套「裝備推高倍率、
> 深釣點比較好賺、滿裝 ×2.5」的平衡邏輯**全部作廢**，連帶整套調參方法論也不再適用。

## 一 · 兩種 RTP 口徑（先對齊定義，其他都建立在這上面）

| 口徑 | 算法 | 值 |
|---|---|---|
| **投注口徑** | 賠付 ÷ 下注額 | Buffer 池空時 = 98%，池有錢時 98%～108% |
| **總體口徑** | 賠付 ÷（下注額 ＋ 商店消費） | **恆為 98%** |

**設計目標是總體口徑 98%。** 做法是讓兩條金流都抽 2%：

```
下注：  每一竿的期望賠付 = bet × 0.98              ← rtpNorm() 保證
商店：  買東西付 P，其中 P × 0.98 進 Buffer 池      ← toBuffer()
        池再由後續的拋竿全額回吐給玩家             ← bufferBoost()

總賠付 = 0.98 × 下注額 + 0.98 × 商店消費 = 0.98 × (下注額 + 商店消費)
```

所以**買裝備不是沉沒成本，是延後領取的賠付**。這句話是整個設計的樞紐——它同時解決了兩件事：商店在數學上變成 RTP 中性（不可能再靠賣裝備破壞平衡），而玩家花掉的錢也確實會回來。

> **簽到、每日任務、儲值贈送的籌碼不列入任何一個口徑。** 那是行銷成本（憑空發出去的錢），
> 不是遊戲賠付。要量真實 RTP 就看 `stats.payout / stats.wagered`，兩個欄位都只記拋竿與賠付。

## 二 · 籌碼流向全圖

```
流入                                 流出                        Buffer 池
──────────────────────────────       ──────────────────────      ───────────────────
賠付（賣魚/收藏）  rollCatch()        下注    wager(bet)          ← 商店消費 × 0.98
每日簽到  claimSignin()    ┐         餌料    buyBait()      ┐
每日任務  claimMission()   ├ 行銷     釣竿    buyRod()       │
籌碼包    buyPack()        ┘ 成本     裝備    buyEquip()     ├→ toBuffer()
                                     魚缸    upgradeTank()  │
                                     裝飾    buyDeco()      ┘
                                                             → bufferBoost() 排回賠付
```

> **釣點解鎖不是流出項**，十六個釣點都免費（[07](07-data-schema.md#為什麼所有釣點都是免費的)）。進程門檻由 `minBet` 承擔。

## 三 · 下注階梯 · `FG.BETS` 與 `loc.minBet`

```js
FG.BETS = [100,200,…,1000, 2000,3000,…,10000]   // 19 檔
```

前段每格 +100、後段每格 +1000，**刻意不用倍增**：倍增的階梯在低檔位跳太快，玩家還沒摸清手感就被推到下一個量級；等差讓「加一格」的心理成本從頭到尾一致。

```js
state.bet(loc)        = max(data.bet, loc.minBet)   // 低於門檻自動抬高
state.betOptions(loc) = FG.BETS.filter(v => v >= loc.minBet)
state.castCost(loc)   = state.bet(loc)              // 拋竿費就是下注額
```

`loc.minBet` 是**舊版 `castCost` 的角色**：它是進程門檻。門檻之上玩家自己決定押多少。晨霧湖 100（19 檔全開）→ 曉日沉港 7,000（剩 4 檔）。

**魚的賠付是「bet 的倍率」（`fish.mult`）而不是絕對籌碼**，所以換 bet 只是等比放大整場遊戲的金額，RTP 完全不動。

## 五 · 加成來源（只剩四個 effect key）

| 來源 | 提供什麼 | 同時生效 |
|---|---|---|
| 釣竿 | `kingMul` `sizeBonus` | **1 支** |
| 餌料 | `jackpotMul` `junkMul` | **1 種** |
| 裝備（通用 5 件） | `jackpotMul` / `kingMul` / `sizeBonus` / `showHint`，**一件一個** | **全部相乘** |
| 裝備（釣點專屬，`effect.loc`） | 同上 | 只在該釣點，等於**同時 1 件** |
| 家園裝飾 | 目前一律純裝飾（`effect: {}`） | — |

| key | 作用 | 玩家看到的文案 |
|---|---|---|
| `jackpotMul` | 乘在**傳說／魚王**這兩階魚的 `mult` 上 | 「大獎倍率 +N%」 |
| `kingMul` | 提高**魚王**的階級權重 | 「魚王出現率 +N%」 |
| `sizeBonus` | 體長分布往上推 | 「體型 +N%」 |
| `junkMul` | 雜物階級權重 | 「雜物 −N%」 |
| `showHint` | 咬鉤前的聲納提示 | 「魚影提示」 |

**單件生效的（竿／餌）幅度可以大，全部相乘的（裝備）必須小。** 竿的 `kingMul` 跨 1.00→2.50、餌的 `jackpotMul` 跨 1.00→1.60；裝備一律只有 **+2%～+5%**，六件同時生效約 ×1.20。

> ⚠️ **餌料不經過 `bonus()` 的舊規則已經取消。** 現在 `bonus()` 內部就把 `bait.jackpotMul` 乘進去了，所以 `bonus(loc).jackpotMul` 已經是最終值，不必再乘一次。但 `junkMul` 仍然只在 `rarityTable()` 裡直接讀 `bait()`——它是階級權重，不屬於 `bonus()`。

### 為什麼裝備不能加 EV（這一節是本頁最重要的）

固定 RTP 的直接後果：**任何裝備都不可能提高期望值，只能改變分布形狀。** 因為 `rtpNorm()` 會把 EV 拉回 `bet × 0.98`（見下方 §七）。所以三個舊 effect key 全部被移除：

| 舊 key | 下場 | 原因 |
|---|---|---|
| `costMul` | **刪除** | 賠付按 `bet` 算、成本按 `bet × costMul` 算，會把 RTP 推到 115%。**這是唯一會真的破壞 98% 的東西。** |
| `valueMul` | **刪除** | 直接乘在賠付上 → 被 `rtpNorm` 等比抵銷 → 完全沒有效果 |
| `rareMul` | **刪除** | 拉高稀有／史詩權重 → 中獎更頻繁但單筆更小 → EV 不變，只是**降低波動**。而「中獎更頻繁」不是玩家想買的東西 |

留著一個沒有效果的效果，比沒有效果更糟——玩家會照著它做決策。

**所以裝備的定位變成「波動度旋鈕」**：`jackpotMul` 把 EV 從小獎搬到大獎，`kingMul` 把 EV 搬到魚王。進程的驅動力剩下三個：**圖鑑收集、魚王 jackpot、解鎖更高的 minBet 檔位**。

> **這也讓「疊乘失控」這個風險永久消失。** 舊版最大的地雷是多個 1.2～2.5 的倍率連乘（[10 §調參歷史](10-balance-tuning.md#調參歷史與教訓) 記過兩次事故）。現在疊再多也只是把 EV 搬來搬去，`rtpNorm` 會吸收掉。`effect.loc` 因此**不再是安全機制**，它現在純粹是內容規則（一釣點一整套周邊）。

## 六 · 稀有度權重表 · `rarityTable(loc)`

```js
K = bonus(loc).kingMul

for 每個「該釣點實際有魚的」稀有度:
  w = RARITY[key].weight
  junk : w *= bait().junkMul
  king : w *= K
  其餘五階：不變
```

**只有兩階的權重會被裝備動到。** 中間五階（common/good/rare/epic/legend）固定不動，理由就是上一節：在固定 RTP 下拉高它們只會讓「中獎更頻繁、單筆更小」。

這張表同時餵給 UI 的費率表，所以玩家看到的機率一定跟實際一致，不會有兩份邏輯。

- **只有該釣點實際存在的稀有度才會進表**。新釣點沒放史詩魚，那 30 點權重就不存在，其他階級的相對機率自動變高。
- 權重歸一化在最後才做（`r.pct = r.weight / total`），任何一階被拉高，其他階都會被稀釋。
- 魚王機率：無裝備 0.200% → 滿配約 **0.58%**（竿 ×2.5 ＋ 裝備約 ×1.05）。

## 七 · 固定 RTP 的核心 · `rtpNorm(loc, rows, boost)`

**這是整個改版的關鍵函式，只有十幾行，但它讓 98% 從「調出來的」變成「算出來的」。**

魚的 `mult` 是相對 bet 的標稱倍率，但實際賠付還會被四件事放大／縮小：

1. 體長係數 `(len/avg)²` —— 期望值隨 `sizeBonus` 變動
2. 閃光 3% ×3 —— 期望倍率固定 **1.06**（雜物不吃）
3. `jackpotMul` —— 只作用在傳說／魚王
4. 階級機率本身被 `junkMul` / `kingMul` 改動

所以每次抽獎前，用**當下的**分布把原始期望倍率算出來：

```
rawEV = Σ_階級 P(階級) × mean_over_fish( mult × jackpotMul? × E[(len/avg)²] × (雜物?1:1.06) )
norm  = (0.98 + boost) / rawEV
賠付   = bet × mult × jackpotMul? × (len/avg)² × norm ×（閃光?3:1）
```

**分子分母同源，所以 `E[賠付] ≡ bet × (0.98 + boost)`——這是恆等式，不是調出來的近似值。** 不管玩家帶什麼竿餌裝備、在哪個釣點、下多少注，都成立。不需要事後校正，也不需要跑模擬確認。

`E[(len/avg)²]` 由 `sizeMoments(sb)` 提供：`t' = clamp(U^2.4 × (1+sb) + sb×0.25, 0, 1)` 的一階與二階動差。`clamp` 讓它沒有漂亮的解析解，所以用 4096 點中點積分，並依 `sizeBonus` 快取（`sizeBonus` 很少變）。

> **副作用：`mult` 的數值本身變成「近似真實倍率」。** `data.js` 的 `mult` 是照「無裝備基礎配置下 `norm ≈ 1.000`」反推出來的（換算腳本會對每個釣點整批縮放），所以基礎配置下 `norm` 實測是 **1.0001**。這讓資料表可讀——看到 `mult: 43.1` 就知道那條魚大約賠 43 倍。裝上裝備之後 `norm` 會偏離 1，因為 EV 被搬去大獎了。

### 驗證方式

**不要用蒙地卡羅去驗總 RTP。** EV 有 8%～60% 壓在機率 0.2%～0.6% 的魚王身上，200 萬竿也只抽到幾千條，標準誤差就有 0.5%，而且分布右偏（多數樣本會低於期望值）——你會追著雜訊調數值。

正確做法是**直接驗恆等式**（腳本在暫存目錄，載入真正的 `util.js`／`data.js`／`state.js` 跑，不另寫公式）：

```
16 釣點 × 21 竿 × 21 餌 × 3 裝備配置 × 各釣點可用的 bet 檔 = 243,432 組
→ RTP 與 0.980000 的最大誤差 4.4e-16（浮點精度極限）
```

要用蒙地卡羅交叉驗證，就拆成兩個低變異的量：**非魚王的賠付**（變異小）與**魚王的出現頻率**（伯努利）。實測 200 萬竿：

| 配置 | 非魚王 EV/bet 模擬 vs 解析 | 魚王率 模擬 vs 解析 |
|---|---|---|
| 晨霧湖 · 無裝備 | 0.9078 vs 0.9054 | 0.200% vs 0.200% |
| 宵櫻神域 · 秘銀竿＋假餌＋通用五件 | 0.6480 vs 0.6514 | 0.428% vs 0.424% |
| 曉日沉港 · 滿裝 | 0.3648 vs 0.3636 | 0.587% vs 0.581% |

## 八 · 抽一次漁獲 · `rollCatch(loc)`

```
1. rows  = rarityTable(loc)
2. boost = bufferBoost(bet)                          ← 立刻扣池，見 §九
   norm  = rtpNorm(loc, rows, boost)
3. row   = weightedPick(rows, r => r.weight)         ← 先抽階級
4. fish  = pick(row.fish)                            ← 階級內「等機率」抽魚種
5. 體型
     t = skewed(2.4)                                 ← pow(random, 2.4)，偏小
     t = clamp(t * (1 + sizeBonus) + sizeBonus*0.25, 0, 1)
     len = minLen + (maxLen - minLen) * t
6. 重量  weight = len^3 * density[shape]              ← 純展示，不參與計算
7. 閃光  shiny = 非雜物 && random < 0.03
8. 賠付  value = bet * payoutMult(fish) * (len/avg)^2 * norm
         shiny → *= 3
```

### 各段的設計理由

**階級內等機率**：同一階級的魚不分軒輊，靠 `mult` 和體長範圍拉開差異。想讓某條魚更罕見，把它升一階，不要在階級內做二次權重——那會讓費率表失真。

**`skewed(2.4)`**：`pow(random, 2.4)` 的分布重心在 0.29 左右，意思是**大部分魚偏小**，釣到接近上限的大物是稀有事件。這讓「同一種魚」也有收集價值（刷最大體長紀錄）。

**`sizeBonus` 的兩段式**：`t * (1+bonus) + bonus*0.25`。乘法讓整條分布拉伸，加法給一個保底抬升，避免小魚永遠是小魚。**在固定 RTP 下它已經不影響收益**（`rtpNorm` 會抵銷），純粹是觀感與圖鑑紀錄。

**重量的 density 表**：
```
normal 2.0e-5 | long 6.0e-6 | round 2.8e-5 | flat 2.4e-5 | wide 2.2e-5 | ray 2.0e-5 | octopus 1.0e-6
```
細長體型（`long`）密度低是符合直覺的——同樣 100cm 的鰻魚比鯉魚輕得多。**重量純粹是展示用。**

**十六種魚王專屬體型裡只有 `octopus` 有自己的一列，其餘全部吃 fallback `2.0e-5`。** 這是刻意的：魚王的重量本來就誇張（世界蛇 900cm 會算出 14 公噸），而那在一條蛇身上讀起來沒問題。章魚是唯一看得出荒謬的——牠的「體長」算的是腕展，而牠幾乎整隻是水，用魚的密度會跑出一公噸多。`1.0e-6` 讓 400cm 腕展落在 64 kg，剛好是真實巨型太平洋章魚的量級。**加新的魚王體型時，先問那個 fallback 在牠身上讀不讀得通。**

**賠付的平方律**：`(len/avg)²`。體長翻倍賠付變 4 倍。用平方而不是立方（雖然重量是立方）是為了不讓大物的賠付誇張到吃掉整個分布。

**閃光 3%**：固定值，不受任何裝備影響。是純粹的驚喜事件，賠付 ×3，期望倍率 1.06 已經算進 `rtpNorm`。

## 九 · Buffer 池 · `toBuffer()` / `bufferBoost()`

```js
// 入池：商店每一筆消費，扣掉 2% 之後全額進池
toBuffer(P):  buffer += P * 0.98

// 排池：墊高該竿的目標 RTP
boost = min(0.10, buffer / (bet * 200))     // 池空 → 0
目標RTP = 0.98 + boost                       // 上限 108%
buffer -= bet * boost                        // ★ 用期望值扣，不是用實際賠付扣
```

**用期望值扣池是關鍵。** `E[多付出去的賠付] = bet × boost`，所以長期收支完全相等；但因為扣的是確定值，**單次中大獎不會把池一次打穿**，池餘額是平滑的指數衰減（每竿排掉 1/200，半衰期約 139 竿）。

`BUFFER_BOOST_MAX = 0.10` 與 `BUFFER_DRAIN = 200` 都在 `state.js` 頂部。兩個都調大會讓回吐更慢、更不容易被察覺。

> 🔇 **Buffer 生效時玩家端完全沒有提示。** 這是刻意的產品決策，不是漏做。
> 代價是玩家不會知道「買裝備的錢回來了」——如果之後要改成有感，最小的改法是頂部列加一個指示，
> 而不是做成獨立的回饋演出（那會變成跟釣魚無關的第二套機制）。

實測（`state.js` 本體跑的）：進池 980,000 → 排空 980,000（誤差 5e-9），用了 15,711 竿。`boost` 從 0 到 0.10 各檔位的 `EV/bet` 分別是 0.980000 / 0.990000 / 1.030000 / 1.080000，誤差 1.1e-16。

## 十 · 寫入紀錄 · `recordCatch(inst)`

```
圖鑑 codex[fishId] → 有就 n++ 並更新 maxLen；沒有就建立
stats.caught++、stats.payout += inst.value、魚王另計 stats.kings++
每日任務：casts +1；稀有以上 → rares +1；isNew → newCodex +1
emit('codex')
```

> **`stats.payout` 記在 `recordCatch()` 而不是 `rollCatch()`**：模擬腳本與開發者面板會直接呼叫 `rollCatch()`，那些不該污染真實統計。對應的分母 `stats.wagered` 記在 `state.wager()`（由 `screen-fishing.js › cast()` 呼叫，**不是 `pay()`**）。

> **`recordCatch()` 和「賣出／收藏」是分開的兩件事。** 圖鑑在釣到的當下就記錄，之後不管賣掉、收藏還是放生都不影響。這是為了讓玩家能安心賣魚。`stats.payout` 同理——收藏起來不賣也算賠付，那是玩家選擇持有資產，不是遊戲少付了。
>
> ⚠️ 手動流程在 `showResult()` 裡呼叫 `recordCatch()`；自動流程在 `resolveAuto()` 裡呼叫。**「魚缸滿了轉交手動」這條路徑會走 `showResult()`，所以 `resolveAuto()` 在那個分支必須跳過 `recordCatch()`，否則會記兩次。** 現行程式碼是靠 early return 處理的，改動時務必保持。
