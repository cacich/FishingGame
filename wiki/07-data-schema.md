# 07 · 資料規格

> 涵蓋：`js/data.js` 全部資料表的欄位定義
> 相關：[09 操作手冊](09-recipes.md)（照步驟新增內容）、[06 像素引擎](06-pixel-engine.md)（美術欄位怎麼影響外觀）

`data.js` 是**純資料，沒有邏輯**。想加內容原則上只動這個檔（例外：裝備／裝飾的圖示在各自的分頁檔，見下）。

---

## 釣點 · `FG.LOCATIONS`

```js
{
  id:          'mist_lake',        // 唯一。存檔的 unlocked[] / data.loc 都存這個
  name:        '晨霧湖',
  subtitle:    '新手釣場 · 靜水',    // 卡片副標
  desc:        '一段介紹文字',        // 選單、圖鑑、解鎖確認框都會用
  seed:        20250803,           // 場景亂數種子。固定值 = 地形與反光每次長一樣
  minBet:      100,                // ★ 最低下注額。必須是 FG.BETS 裡的某一格
  unlock:      { free: true } | { chips: 120000 },   // 目前二十個釣點都是 free
  comingSoon:  false,              // true → 選單顯示「即將開放」，不可進入也不可解鎖
  scene:       { terrain: 'forest', ...調色盤... },
  fish:        [ ...魚陣列... ]
}
```

查詢用 `FG.locById(id)`（查不到回第一個地點，不會 throw）。

### 下注階梯 · `FG.BETS`

```js
FG.BETS = [100,200,300,400,500,600,700,800,900,1000, 2000,3000,4000,5000,6000,7000,8000,9000,10000,11000,12000]
```

21 檔，前段每格 +100、後段每格 +1000，**刻意不用倍增**（理由見 [03 §三](03-economy.md#三--下注階梯--fgbets-與-locminbet)）。玩家在釣魚畫面選一格，`state.bet(loc)` 會把低於 `loc.minBet` 的選擇自動抬高，`state.betOptions(loc)` 只列出該釣點可用的檔位。

`loc.minBet` 是**舊版 `castCost` 的角色**——它是進程門檻，門檻之上玩家自己決定押多少。

> 🔴 **`castCost` 這個欄位已經不存在了。** `state.castCost(loc)` 還在，但它現在只是 `state.bet(loc)` 的別名（拋竿費 = 下注額）。

**最深的釣點刻意停在 11,000 而不是階梯頂端 12,000**，讓終點站仍保留一格加注空間。前十個釣點各佔 100 那一段的一格，後十個佔 1000 那一段。

> ★ **每個釣點都必須有一整套專屬內容與正式美術**：主題釣竿、主題餌料、專屬裝備、主題家園裝飾、魚王 cut-in、場景背景／縮圖，以及每個魚／雜物的 PNG 精靈。程序化繪製只供載入失敗備援；完整交付規格見 [09 §新增一個釣點](09-recipes.md#新增一個釣點--一次要生出一整套)。

**陣列順序 = 進程順序 = 各處 UI 的顯示順序**，並且與 `minBet` 遞增一致。劍影寒潭與敦煌月泉接在尾端，補上 10,000／11,000 兩格；所有跨檔案參照都使用 `loc.id`（`data.loc`、`unlocked[]`、`bgCache`、魚的 id 前綴），不把永久狀態綁在索引上。唯一的索引是 `screen-codex.js › locIdx`，它每次 `onShow()` 都由 `data.loc` 重算。

> ⚠️ **插隊比接尾難，而且會越來越難。** 滿裝倍率必須單調遞增，而那條曲線已經收斂到 2.39 → 2.41 → 2.46 → 2.51——插在中間的釣點，可用的倍率窗口只有 **0.02～0.05**，比蒙地卡羅模擬的噪音還小。**插隊前一定要先用 [10 §精確版](10-balance-tuning.md#精確版不用模擬直接把期望值算出來) 量一次窗口還有多寬。**
>
> **但前段還很鬆。** 2026-08-05 新增的兩個插隊釣點（亂石急湍 900、琉璃珊瑚 1,400）用掉的是 (2.082, 2.256) 與 (2.256, 2.389) 這兩個窗口，寬度 0.174 / 0.133——比後段寬一個數量級。**要插隊就往前段插**，2,300 以後那幾段（最窄剩 0.009）實務上已經插不下了。

> **終點現在是敦煌月泉**（minBet 11,000）。歷次接尾的釣點文案都避免宣稱自己是「最深」或「最後」；未來再加釣點也要維持這個做法。

「圖鑑分母」是 `codexProgress()` 算出來的數字，**雜物不列入**（見 [02 §圖鑑](02-state-and-save.md)）。所有釣點的圖鑑分母都刻意維持在 20 以上，讓每張圖鑑頁的收集進度條長度感覺一致。

**每個釣點都有專屬的 `terrain`**，不是只換調色盤——地形產生器與各自的設計理由見 [06 §地形系統](06-pixel-engine.md#三之二--地形系統--terrain)。

> ⚠️ **釣點名稱長度會撞到 UI。** 四個中文字的釣點名在 320px 級的螢幕上會把圖鑑的釣點切換列擠到折行。這已經用橫向捲動解決（見 [08 §會隨釣點數量成長的介面](08-ui-and-screens.md#會隨釣點數量成長的介面)），但**新釣點的 `name` 還是建議控制在 4 個字以內**，`subtitle` 控制在 8 個字以內。

### 為什麼所有釣點都是免費的

**進程門檻由 `castCost` 承擔，不由解鎖費承擔。** 拋竿費從 400 一路到 96,000（240 倍），開局 20,000 籌碼在鐘乳暗穴連一竿都拋不動，光是這點就足以讓玩家自然待在負擔得起的釣點。再疊一層一次性解鎖費只是多一道「存錢等待」的空轉，不會讓決策變有趣。

這樣設計還有兩個好處：新玩家可以馬上進去看看深淵長什麼樣（內容是這個遊戲的賣點，沒理由藏起來）；而且「今天想拚魚王就去深淵、想穩穩賺就回晨霧湖」變成一個**每一竿都能重做的選擇**，而不是一次性的解鎖決定。

`unlock: { chips: N }` 的機制本身**沒有被移除**，`state.js › unlockLoc()`、`data.unlocked[]` 與兩處 UI 的解鎖按鈕都還在，把任何一個釣點改回 `{ chips: N }` 就會立刻恢復收費。

> ⚠️ **`isUnlocked()` 對 `unlock.free` 是直接回 true，不看 `data.unlocked[]`。** 所以改成免費不需要遷移舊存檔（舊存檔的 `unlocked` 仍然只有 `['mist_lake']`，但所有釣點都進得去），改回收費也不會讓已付費的玩家重付。

`comingSoon` 目前**沒有任何釣點在用**（二十個都已開放），欄位保留給未來新增的預告釣點。相關的 `unlockLoc()` 回傳值 `'soon'` 與兩處 UI 的「即將開放」分支都還在，加新的預告釣點時可以直接沿用。

`art` 的欄位：

目前二十筆 `FG.LOCATIONS[].scene` 都有 `art`。這不是刪除程序化場景，而是為每個釣點提供一致的正式美術與可離線預快取的縮圖。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `background` | 相對路徑 | `200×340` 的不透明 PNG，只含靜態場景；不得含船、人物、釣具、魚、文字或 UI |
| `thumbnail` | 相對路徑 | `76×50` 的橫式釣點縮圖，用於釣點選單、每日頁與家園掛畫 |
| `horizon` | 0～1（選用） | 點陣主圖的實際水線。省略時沿用外層 `scene.horizon` |

即使有 `art`，`terrain` 與整套調色盤也不能刪：它們是圖片載入前、缺檔、`file://` 瀏覽器限制或離線快取不完整時的可玩備援；`highlight`／`highlight2` 與船身三色也仍由逐幀動態層使用。

`farTree` / `midTree` / `nearTree` 是**由遠而近的三層剪影色**，名字沿用自最早的樹林實作；在其他地形裡它們分別代表崖壁層、冰川與冰脊、櫻花林等等。改名會動到二十個釣點的資料，**目前刻意不改**——知道這件事就好。

| `bamboo` `swordLight` | `wuxia` | 竹影與水面劍光。劍光要比水面高一階，但不能亮到蓋過浮標 |
| `grotto` `cave` `lamp` | `dunhuang` | 石窟崖、拱龕暗部與龕中燈火；規則明暗交替是蜂巢感的核心 |
| `temple` `ribbon` `yardang` | `dunhuang` | 前景殿影、飛天長綾色票與雅丹石柱；`ribbon` 是色碼陣列，維持赭金／絳紫／青綠三色而不走霓虹 |

> ⚠️ **`karst` 的白牆（`wall`）與霧帶（`mist`）不會有倒影。** 倒影只保留亮度 ≤ 150 的像素（見 [06 §為什麼倒影用 getImageData](06-pixel-engine.md#為什麼倒影用-getimagedata)），這兩個色都遠高於門檻。這是刻意接受的：白牆在水裡鏡射會亮到蓋掉水面，霧本來也不該有倒影。要讓某個新地形物件有倒影，它的顏色就必須壓在 150 以下。

配色訣竅：`waterTop` 要比 `waterBot` 暗（遠處水面反射天空較深），否則景深會反過來。

## 魚 · `location.fish[]`

### 一般魚

```js
{
  id:      'ml_bass',      // 唯一！同時是圖鑑 key 與精靈快取 key
  name:    '黑鱸',
  rarity:  'good',         // junk|common|good|rare|epic|legend|king
  shape:   'normal',       // normal|long|round|flat|wide|ray|slim|crest|boxy|torpedo
                           // 魚王專屬另含 catfish…octopus、jianlong、moon_koi
                           //           lungfish|koi|skipper|leaper|coelacanth
                           //           clinger|wrasse|olm|octopus
  scale:   0.9,            // 在精靈框中的佔比，魚王建議 1.25～1.35
  pattern: 'band',         // none|stripe|band|band2|spot|speck|net|scale|gradient|saddle|ocellus|chevron
  special: ['glow'],       // 選用：glow|spike|whisker|scar|horn|jaw|lantern
                           //       finlet|mane|frost|rostrum|forkTongue|filaments
                           //       stalkEye|kype|lobeFin|sucker|hump|gills|limbs|blind
                           //       arms|slitEye
  cyOffset: 1,             // 選用：垂直微調（像素）
  mult:    2.13,           // ★ 賠付倍率（相對「下注額」，不是絕對籌碼）
  minLen:  25, maxLen: 50, // 體長範圍（cm）
  colors:  { body, back, belly, fin, pattern, glow, hornColor,
             scar, tooth, frost, lantern, mane, rostrum, tongue, filament,  // 各 special 的專屬色，省略有預設值
             kype, lobe, sucker, hump, gill, limb, arm,
             eyeWhite, pupil },
  desc:    '一句描述',
  legend:  '長篇傳說文字'    // 選用。有的話結果卡與圖鑑會用琥珀色框強調
}
```

**只有 `colors.body` 是必填**，其餘會自動由它推導（見 [06 §上色](06-pixel-engine.md#上色)）。

> 🔴 **`value` 已改名為 `mult` 並改變語意（2026-08-06）。** 舊的 `value` 是絕對籌碼，
> 新的 `mult` 是**相對下注額的倍率**——實際賠付是
> `bet × mult × (len/avg)² × rtpNorm × (閃光?3:1)`。這樣換 bet 只是等比放大金額，RTP 不動。
>
> **`mult` 不是手填的**，是用換算腳本從一條波動度曲線生出來的（見 [10 §波動度曲線](10-balance-tuning.md#波動度曲線唯一真正要調的東西)）。
> 手改單一條魚的 `mult` 是安全的（`rtpNorm` 會把總 EV 拉回 0.98），但它會**稀釋同階其他魚的賠付**——
> 想讓某條魚特別值錢，正確做法是把它升一階。

> **一般魚的 `shape`／`pattern` 分布要定期檢查，不要只憑感覺加。** 2026-08-06 之前 `long` 一種就佔掉全部非魚王魚的 36%（`cavern` 單一釣點 10/19），`pattern: 'none'` 佔 26%——都是因為每次加魚都順手抓最熟悉的組合，沒人統計過整體分布。查法：`node` 讀 `data.js`（`window.FG=...; eval(fs.readFileSync(...))`）後對 `FG.LOCATIONS` 裡每條非魚王、非雜物魚的 `shape`／`pattern` 計數。那次順便把 6 種一般魚 shape 擴到 10 種、8 種 pattern 擴到 12 種（見 [06 §體型輪廓表](06-pixel-engine.md#體型輪廓表--shapes)、[06 §花紋](06-pixel-engine.md#花紋--pattern)），並重新分配了約 60 條現有魚。**改現有魚的 `shape`／`pattern` 不影響機率也不影響期望值**（[11 §14](11-invariants-and-gotchas.md#14-加魚不改機率但會改期望值) 講的是「加魚」，換現有魚的造型欄位純粹是外觀），但兩個釣點要注意：`coral_reef` 的稀有度是靠輪廓分階（junk～good 只能用 `flat`/`long`/`wide`/`round`，見下方 [§琉璃珊瑚](#琉璃珊瑚唯一一個不用顏色分階的釣點)），`cavern` 全場 `pattern` 刻意留 `none`（半透明無色是識別，見 [§鐘乳暗穴](#鐘乳暗穴唯一一個高階不發光的暗色釣點)）——這兩個釣點改的時候要繞開各自的識別軸。

`id` 命名慣例：釣點前綴 + 底線 + 名稱（前綴對照見上方釣點表）。**id 一旦上線就不要改**，改了等於玩家的圖鑑紀錄消失。

### 一個釣點該放幾條魚

現行二十個釣點都採同一套配額，**不是隨便長出來的**：

| 稀有度 | 每個釣點的魚種數 | 理由 |
|---|---|---|
| junk | 3 | 夠讓「又是垃圾」有點變化，又不會洗版 |
| common | 6 | 佔 52% 抽獎權重，是玩家看最多次的一階，種類最多 |
| good | 5 | 26% 權重 |
| rare | 4 | 9% 權重 |
| epic | 2～3 | 3% 權重。再多會讓單一種類的出現間隔長到沒有記憶點 |
| legend | 2 | 0.8% 權重。兩條剛好構成「還差一條」的收集張力 |
| king | 1 | **每個釣點固定一位**，是該釣點的招牌 |

> **四種「長條形」與四種「大尾巴」怎麼不互相撞**，見 [06 §體型輪廓表](06-pixel-engine.md#體型輪廓表--shapes) 下方的對照。簡單說：長條形靠**鰭緣的分布**分（`long` 集中／`serpent` 沒有／`lungfish` 後半連續／`dragon` 有鬃），大尾巴靠 **`fork`** 分（`tuna` .72 深叉／`leaper` .52 月牙／`koi` .10 飄紗）。

> **`serpent` 與 `dragon` 是刻意區分開的兩種「長條形」。** `dragon`（八尋）有 `tailH .95` 的大尾扇與 `mane` 的高聳鬃毛，是「帶狀的魚」；`serpent`（耶夢加得）`tailH .14`、`dorsal .05`、`e .30`，是「粗細均勻、沒有鰭、尾巴收成一點」的真蛇。兩者放在一起不會被認成同一條。

**`scar` 只給翁德。** 牠的傳說明寫「背上那道疤」，是角色設定；其他魚王沒有這段故事，加了只會讓牠們看起來像同一張貼圖換色。這是實際踩過的坑——初版五王全是 `shape: 'wide'` + `glow` + `scar`，只有配色不同，並排在圖鑑裡完全認不出是不同的魚。詳見 [11 §五王同型](11-invariants-and-gotchas.md)。

`glow` 是**唯一所有魚王共用的 special**，它是「這條是魚王」的統一訊號，刻意保留。

> **`colors.glow` 還有第二個用途**：它是那位魚王 cut-in 的主色，`colors.pattern` 是輔色（`cutin.js` 直接讀，不另外設定）。所以調魚王配色會連帶改掉牠的登場演出色調——這是刻意的，一條魚只有一套顏色。分配表見 [04 §cut-in](04-fishing-loop.md#cut-in--傳說以上的登場演出)。

**每位魚王還要在 `cutin.js › KING` 有一筆**（`motif` / `particle` / `title` / `tone`），決定登場演出的骨架、粒子動線、標語與音階；它是新增釣點整套內容的一部分，步驟見 [09 §新增一個釣點](09-recipes.md#新增一個釣點--一次要生出一整套)。

**每一筆 `fish.id` 都有正式美術路徑契約**：`assets/sprites/<location id 的底線改連字號>/<fish.id>.png`。檔案固定為 96×56 RGBA、透明背景、單一主體；魚頭朝右，`junkArt` 雜物不受朝向限制。`pixel.js` 會自動推導路徑，不需要在資料表另寫欄位，但「能由程序化精靈備援顯示」不代表資產可以缺席。新增魚或新釣點時必須連同 PNG、`sw.js › ASSETS` 與 `VERSION` 一起更新。

**關鍵：階級內是等機率抽的（[03 §rollCatch](03-economy.md#抽一次漁獲--rollcatchloc)），所以往同一階級加魚不會改變該階級的總機率，只會稀釋單一魚種的出現率。** 高階級放太多種，玩家會覺得「傳說魚都湊不齊」；低階級放太少，又會重複到膩。上面的配額就是照這個取捨定的。

### 雜物

```js
{
  id: 'ml_boot', name: '破舊長靴', rarity: 'junk',
  junkArt: 'boot',      // boot | can | weed | bottle | ice | bone | ema | porthole …（完整清單見 06 §雜物字元圖清單）
  value: 12, minLen: 20, maxLen: 34,
  unit: 'cm',           // 目前未使用，保留欄位
  desc: '…'
}
```

有 `junkArt` 的項目會走 `buildJunk()`，**不吃 shape/colors/pattern**，也不列入圖鑑分母、不會被閃光、不套 `valueMul`。

雜物美術**不得跨釣點複用**：每個釣點的三件雜物都要各有一個 `junkArt`，並分別表達環境自然物、當地活動痕跡與帶故事感的人造物。雜物雖然是負面事件，卻是玩家最常看到、也最容易建立「我現在在哪裡」印象的物件；若只換 `name`／`desc` 而沿用鐵罐、水草或玻璃瓶剪影，文字設定不會真的進入畫面。完整的對照表見 [06 §雜物字元圖清單](06-pixel-engine.md#雜物字元圖清單--junk_maps)。

查詢用 `FG.fishById(id)`，會掃過所有地點。

### 各釣點的配色規則

魚的辨識度靠**釣點內的一致性**與**階級之間的對比**，不是靠每條魚各自好看：

| 釣點 | 底色調 | 對比手法 |
|---|---|---|
| 晨霧湖 | 灰藍／土黃的自然色 | 稀有以上開始出現紫、金、純白 |
| 澄澈方池 | **反過來**：普通階全是灰褐的野雜魚與飼料魚 | **人工選育的鮮豔色（紅白、朱、金、白）是高階的訊號**。別的釣點是「同色系拉明度」，這裡是「養的 vs 野的」 |
| 潮落礁灘 | 礁岩的褐綠 × 濕沙的灰白 | 稀有以上換成**潮池裡的螢光色**（海葵桃紅、孔雀藍、鸚哥青綠），在一整片灰褐裡直接跳出來 |
| 亂石急湍 | 溪石的灰白 × 苔綠 | 稀有以上開始出現**虹彩**（金屬般的反光）。急流整天都是翻捲的白水，色素在那裡沒有用，只有反光閃得出來 |
| 琉璃珊瑚 | **全遊戲飽和度最高**，桃紅／橙黃／青綠／藍紫在普通階就全上了 | **不靠顏色分階——改用輪廓**。詳見下一節 |
| 鐘乳暗穴 | 乳白與半透明的粉肉色，唯一的顏色是鰓部血管透出來的紅 | **稀有以上不給 `glow`**（全遊戲唯一）。詳見下一節 |
| 曉日沉港 | 鏽褐 × 油污灰綠（普通～優良） | 稀有以上換成**船漆的人工色**（信號旗紅、警示黃、鉛丹橘、艙藍）。**顏色不是天然的，是漆的顏色**——每一則 `desc` 都在解釋那身顏色抄自船上的哪一塊漆。跟黃沙冥河的「整片暖色」不同：這裡低階是灰的，高階才跳出人工色 |
| 懸瀑深潭 | 深潭的墨綠 × 白沫 | 稀有以上開始出現**婚姻色**（緋紅、青綠）——溯河產卵的魚才會換上那身顏色 |
| 硫煙湯湖 | 玄武岩的黑紫 × 硫磺黃 × 溫泉乳青 | 稀有以上一律帶 `glow`，而且是**暖光**。這是刻意跟深淵海溝對照：那裡是「沒有光所以自己發冷光」，這裡是「太燙所以自己在發熱」 |
| 宵櫻神域 | 朱紅 × 櫻粉 × 墨黑的和風三色 | 稀有以上多用金與朱；汽水域所以淡水鹹水魚種混編 |
| 落霞峽灣 | 藍綠海色，點綴橘金 | 傳說用大面積暖色（霞光魟、皇帶魚） |
| 幽藍冰湖 | **全部壓在藍白冷調** | 暖色（橘點、紫鰭）只給優良以上，玩家一眼認得出「這條不一樣」 |
| 煙雨蓮江 | **水墨色域**：墨青、灰藍、青瓷綠 | 暖色（朱紅、胭脂、金）只給稀有以上。整片灰綠打底，所以一條胭脂魚或金鯉會非常突出 |
| 深淵海溝 | **底色壓到接近黑** | 辨識度全靠 `special: ['glow']` 與冷光 `pattern`；沒有陽光的地方不會有保護色，所以幾乎每種都帶生物發光 |
| 世界樹根 | 極夜的深藍黑，**唯一亮色來源是極光**（青綠 × 紫） | 用「**魚種性質**」而不是配色分界：普通～優良是北大西洋真實冷水魚、一律銀白灰；史詩以上換成神話生物、帶 `glow` 並吃極光的青綠紫金 |
| 黃沙冥河 | **全遊戲唯一整片暖色**：赭黃、砂金、落日橘 | 其他十一個釣點都偏冷或偏灰，所以這裡反過來——**冷色（青金石藍、綠松石、月銀）成為稀有以上的訊號**。同樣用「真實尼羅河魚種 → 古埃及神話」做史詩以上的分界 |

### 琉璃珊瑚：唯一一個「不用顏色分階」的釣點

其他十五個釣點的稀有度對比都靠顏色——不是「灰底 + 高階跳色」（潮落礁灘、幽藍冰湖、煙雨蓮江），就是「換掉魚的種類順便換色系」（世界樹根、黃沙冥河）。**琉璃珊瑚沒有這個選項**：普通階的雀鯛、豆娘魚、刺尾鯛已經用掉了電光藍、鮮黃、橘配黑，飽和度已經拉到頂，**沒有更鮮豔的顏色可以留給高階**。

所以它改用**輪廓**分階：

- junk～good：都是「一般魚的形狀」（`flat` `long` `wide` `round`），差別只在花色。
- rare 以上：一律是**體型或造型異常**的——蓑鮋散開的十八根鰭棘、裸胸鱔的長管身、魟的圓盤、角鼻魚額頭那根角、蝠鱝的翼。
- legend／king：直接上全畫面最大的剪影（暗礁蝠鱝 400cm、蘇眉的額隆）。

**這條分階手法是新的，不要退回配色。** 把高階的顏色調得更豔沒有用（已經滿了），把低階調灰更糟——那會直接毀掉這個釣點唯一的識別（見 [06 §reef 的三個設計決定](06-pixel-engine.md#reef-的三個設計決定)：地形那邊也是靠高飽和撐起來的）。

同一條軸也決定了每則 `desc` 怎麼寫：**每一則都在解釋那身顏色是幹什麼用的**（給同種看的、打散輪廓的、在十公尺深等於隱形的、清潔站的招牌、警告用的）。這比「牠住在哪」好寫，因為珊瑚礁的魚每一種都真的有一個顏色的理由。

### 鐘乳暗穴：唯一一個高階不發光的暗色釣點

深淵海溝與鐘乳暗穴都是「沒有光的地方」，但兩者的答案剛好相反：

| | 深淵海溝 | 鐘乳暗穴 |
|---|---|---|
| 生物的對策 | **沒有光，所以自己發光** | **沒有光，所以放棄了光** |
| 配色 | 底色壓到接近黑 | 全部乳白／半透明的粉肉色 |
| `special` | 幾乎每種都帶 `glow` | **一律不帶 `glow`**，改帶 `blind` |
| 為什麼成立 | 極暗底色下沒有光暈的話整格圖鑑是一團黑 | 白色的魚在全黑的洞裡本來就是最高對比，不需要光暈 |

**魚王是唯一的例外**：`glow` 是「這條是魚王」的統一訊號（見上方 §二十位魚王），為了那個訊號保留。

魚種的共同軸是「**每一條都失去了某樣東西**」——眼睛、色素、鰾、鱗片、晝夜節律、速度、選擇。這條軸直接給了每則 `desc` 第一句話（「牠失去的是⋯⋯」），是目前所有釣點裡最好寫的一條。

### 曉日沉港：軸是「住在什麼裡面」，不是「住在哪裡」

其他釣點的魚種軸講的是**環境**（哪條江、哪種水、缺了什麼），這一個講的是**容器**：每一條魚都住在一件人造物裡面，而且那件人造物決定了牠的形狀、大小或顏色。

- 形狀：膠管鰻長成那條橡膠管的形狀、鐵板鰈壓得比同種扁。
- 大小：排管鳚一輩子能長多大由管口直徑決定，所以同一排管子裡的每一條都一樣長。
- 顏色：鏽斑杜父魚照著那一塊鏽長、信號旗笛鯛身上那道白帶抄自船上掛的旗。

**這條軸同時解決了配色問題**：稀有以上一律上「船漆的人工色」（見上方配色規則表），而理由就寫在 `desc` 裡——那是漆的顏色，不是魚的顏色。低階維持鏽褐與油污灰綠，所以一條信號旗紅或警示黃出水的時候會非常明顯。

> 這也是為什麼這個釣點的魚王是一隻**章魚**而不是魚：章魚是真的會住進陶壺、而且會把壺搬來搬去排整齊的動物。「住在人造物裡」這條軸推到極致就是牠。

### 世界樹根的分界線就是它的識別方式

多數釣點的稀有度對比靠「同一個色系裡的明度／彩度差」，這裡改成**換掉魚的種類**：

- junk～good：銀鯡、毛鱗魚、圓鰭魚、北海鰈、北洋鱈、狼牙魚、角鯊——全部是真實存在的北大西洋冷水魚，配色一律壓在銀白灰。
- epic 以上：噬根幼龍（尼德霍格的幼體）、島鯨幼體（Lyngbakr）、詭火鮭「洛基」、詩人蜜酒鰻、世界蛇「耶夢加得」——全部出自北歐神話，配色改吃極光的青綠紫與蜜酒金，並且全部帶 `glow`。

**那道分界本身就是玩家讀到的訊息**：「越過某條線之後，釣起來的東西就不是普通的魚了」。這是這個釣點作為終點站要傳達的感覺，也讓它跟深淵海溝（那裡是**全部**都不像魚）區分開來。

### 煙雨蓮江的另一條識別線：真實物種

其他釣點的身分是「什麼環境」（高原湖、峽灣、潟湖、冰湖、海溝），煙雨蓮江的身分是**「哪條江」**——魚種全部取自中國江河的真實物種（麥穗魚、鰟鮍、武昌魴、翹嘴鮊、鱖、胭脂魚、中華鱘、鰣、大鯢、白鱘），`desc` 帶的是這些魚在當地生活裡的位置而不是生態說明。

這樣做的原因：這個釣點在進程上夾在冰湖與深淵之間，如果又靠「奇幻程度」往上加，就會跟深淵的方向撞車。改成往**寫實**的方向走，辨識度來自「這些名字是真的」。

> 後來的釣點沿用了同一招，各自綁一個「這裡的魚有什麼共同點」的軸，而不是綁色系：**澄澈方池**＝每一條都是有人養的、**潮落礁灘**＝每一條都在等漲潮（耐乾、能爬、能鑽沙）、**懸瀑深潭**＝每一條都在往上（能逆流、能跳、能吸附）、**鐘乳暗穴**＝每一條都失去了某樣東西、**曉日沉港**＝每一條都住在人造的東西裡（輪胎、排水管、貨櫃、錨鏈、鍋爐、陶壺）。**這條軸比配色更容易寫出好的 `desc`**，因為它直接給了每條魚一句話的方向。

深淵的魚幾乎全帶 `glow` 是**設計而非偷懶**：`buildFish()` 的反蔭蔽在極暗底色下幾乎看不出來，沒有光暈的話整格圖鑑會是一團黑。

## 裝備 · `FG.EQUIPS`


| `eq_dunhuanglamp` | 440,000 | `kingMul: 1.050` | 敦煌月泉 |

**專屬裝備輪流給 `jackpotMul` 與 `kingMul`**，讓每件有自己的個性。副作用是各釣點的魚王機率會有小鋸齒（0.553% / 0.565% 交錯），那是刻意接受的。

> **陣列刻意分成兩段**（通用五件在前、專屬二十件在後），所以整體 price **不是**遞增的。這沒有影響——`equipIcon()` 是用 `EQUIP_ART[e.id]` 查表，不吃 index。**新的專屬裝備照釣點進程順序插進第二段**，不用跟第一段合併。

> 🔴 **`costMul` / `valueMul` / `rareMul` 三個 effect key 已全部移除。**
> `costMul` 是**唯一真的會破壞 98%** 的東西（賠付按 bet 算、成本按 bet×costMul 算，會把 RTP 推到 115%）；
> 另外兩個會被 `rtpNorm` 抵銷成沒有效果。三件受影響的裝備（防水背心／破冰鑽／溫泉浮台）已改成別的效果。

**兩條規則（理由都變了，但規則保留）**：

1. **釣點專屬裝備一律綁 `effect.loc`。** 舊理由是防疊乘失控——**那個風險在固定 RTP 下已經不存在**（`rtpNorm` 會吸收）。現在的理由純粹是內容規則：一釣點一整套周邊，讓每個釣點保有自己的一件東西。
2. **每件只給一個效果。** 舊理由是兩個乘數會把倍率曲線推高兩成（初版黃沙冥河跑出 ×3.13）。現在的理由是**玩家看得懂**——一件裝備一句話講得完。

> 新增裝備要**同時**在 `screen-shop.js › EQUIP_ART` 加一張 16×9 字元圖，否則圖示是空白。

## 籌碼包 · `FG.PACKS`

```js
{ id, name, chips, bonus, price, once?, extra?, note? }
```

- `price` 是**顯示用字串**（`'NT$30'`），沒有實際金流。
- `once: true` → 限購一次，用 `data.packsBought[id]` 判斷。
- `extra: { rod: 'rod_carbon', baits: { bait_shrimp: 20 } }` → 附贈物品。
- 按下去直接發放（`state.buyPack()`），彈窗頂部有明確的測試版警語。

**要接金流時，唯一要改的是 `main.js › openTopup()` 的按鈕 onClick**，把 `st.buyPack(p)` 換成付款流程的 callback。`buyPack()` 本身可以當成「付款成功後的發貨函式」直接沿用。

## 簽到 · `FG.SIGNIN`

七天循環：`{ day, chips, bait?: { id, n } }`。索引由 `signin.streak % 7` 決定。

## 每日任務 · `FG.MISSIONS`

```js
{ id, name, target, reward, track }
```

`track` 是進度計數的 key，必須跟 `state.js` 裡呼叫 `bumpMission()` 的字串對得上：

| track | 累加時機 |
|---|---|
| `casts` | `recordCatch()`（每次釣獲） |
| `sells` | `sell()` |
| `rares` | `recordCatch()`，稀有度 ≥ rare |
| `newCodex` | `recordCatch()`，`inst.isNew` |

新增任務若需要新的 track，要在 `state.js` 對應的地方補 `bumpMission('新track', 1)`。
