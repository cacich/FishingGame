# 06 · 像素引擎

> 涵蓋：`js/pixel.js`（1460 行，全專案最大的檔案）
> 相關：[07 資料規格](07-data-schema.md)（魚的欄位）、[09 操作手冊](09-recipes.md)

**專案裡沒有任何圖片檔。** 所有美術都是 canvas 在低解析度上逐像素畫出來，再交給 CSS `image-rendering: pixelated` 整數放大。這是整個專案最核心的技術決策——加內容的成本因此接近零。

## 三種產圖方式

| 方式 | 用途 | 入口 |
|---|---|---|
| **字元圖**（char map） | 固定造型的小物：介面圖示、雜物、人物、水豚、裝備／裝飾圖示 | `px.drawMap()` |
| **程序化生成** | 魚：由參數算出輪廓與上色 | `px.sprite()` → `buildFish()` |
| **參數化繪製** | 場景：釣點風景、家園房間、地點縮圖 | `px.drawScene()` / `drawRoom()` / `locThumb()` |

## 基礎工具

```js
px.make(w, h)                          // 建立 canvas，關掉 smoothing
px.drawMap(ctx, map, pal, ox, oy, s)   // 畫字元圖
px.mapSize(map)                        // 回 { w, h }
px.hashStr(s)                          // FNV-1a，把 id 轉成穩定的數字種子
```

## 一 · 字元圖

用字串陣列描述圖案，一個字元一像素，配一張 `{ 字元: 色碼 }` 調色盤。**點（`.`）或不在調色盤裡的字元 = 透明**。

```js
const HEART = {
  pal: { r: '#e2555f', l: '#f18c93' },
  map: [
    '.rr.rr.',
    'rlrrrrr',
    'rrrrrrr',
    '.rrrrr.',
    '..rrr..',
    '...r...'
  ]
};
px.drawMap(ctx, HEART.map, HEART.pal, x, y, 1);
```

### 字元圖清單與所在檔案

| 常數 | 檔案 | 尺寸 | 用途 |
|---|---|---|---|
| `ICONS` | pixel.js | 12×12 / 10×10 | `fish` `calendar` `house` `bag` `book` `coin` — 底部導覽與頂部籌碼圖示 |
| `JUNK_MAPS` | pixel.js | ~10×16 | `boot` `can` `weed` `bottle` `ice` `bone` `ema` — 雜物 |
| `ANGLER` | pixel.js | 11×14 | 船上的釣手 |
| `CAPY` | pixel.js | 16×10 | 水豚（船上＋家園各一份） |
| `HEART` | pixel.js | 7×6 | 水豚頭上的愛心 |
| `EQUIP_ART` | **screen-shop.js** | 16×9 | 五件裝備的圖示 |
| `DECO_ART` | **screen-home.js** | 16×8 | 六種裝飾的圖示 |

> 裝備／裝飾圖示放在各自的分頁檔而不是 pixel.js，因為它們純粹是那個分頁的 UI 素材。加新裝備要記得**同時**加資料（data.js）和圖示（screen-shop.js）。

`px.icon(name, scale, color, accent)` 會回傳放大好的 canvas，`X` 是主色、`a` 是輔色。

## 二 · 程序化魚類生成

`buildFish(f)` 是全檔最複雜的函式。輸入一筆魚的資料定義，輸出一張面向右的像素精靈。

### 畫布規格

```js
SPR_W = 96, SPR_H = 56, MARGIN = 4     // 所有魚共用同一張畫布尺寸
usableW = 96 - 8 = 88
```

**所有魚都畫在同尺寸畫布上**，體型差異靠 `scale` 參數控制佔比。這樣圖鑑格子、結果卡、魚缸裡並排時，大魚看起來就是比較大隻，不需要額外處理縮放。

```js
sc = min(f.scale, 0.98 / (S.bodyLen + S.tailLen))   // 夾住，避免撐出畫面
```

**四種「長條形」怎麼互相分開**——靠鰭緣的分布，不是靠長度：

| | 鰭 | 讀起來像 |
|---|---|---|
| `long` | `dorsal`/`anal` 短而集中在中段 | 一般的細長魚（鰻、梭子魚） |
| `serpent` | `dorsal .05` / `anal .04`＝等於沒有 | 蛇 |
| `lungfish` | `dorsalAt [.02,.58]`＋`analAt [.02,.48]`，高度中等 | **後半身包著一圈連續鰭緣**的原始魚 |
| `dragon` | `dorsal .52` 長而低，再加 `mane` | 帶狀的龍 |

**四種「大尾巴」怎麼互相分開**——靠 `fork`，不是靠 `tailH`：

| | tailLen | tailH | fork | 讀起來像 |
|---|---|---|---|---|
| `tuna` | .22 | 1.05 | **.72** | 深 V 的月牙，速度感 |
| `leaper` | .28 | 1.02 | **.52** | 中等開叉的大月牙，力量感 |
| `koi` | **.30** | **1.18** | **.10** | 幾乎不開叉的一整片紗，觀賞感 |
| `ray` | .36 | .03 | .00 | 一根鞭子（不是尾扇） |

**`coelacanth` 怎麼跟 `catfish` 分開**：兩者都是粗壯的中型身。差別在 `gamma`——`catfish` 1.42 把最寬處推到 t≈0.61（大頭收尾），`coelacanth` 1.02 讓最寬處落在 t≈0.51，**是全部十八種輪廓裡唯一「正中央最寬」的**。配上 `e .36` 的方剖面，讀起來就是一個兩端一樣粗的木桶，而不是一顆頭拖著身體。

**`skipper` 怎麼跟 `abyss` 分開**：兩者的 `gamma` 都偏大（大頭）。差別在背鰭與尾巴——`abyss` 是 `dorsal .24` ＋ `tailH .48` 的小尾，`skipper` 是 `dorsal .70`（**全檔最大**）從 `.08` 一路鋪到 `.78`，加上完全不分叉的圓槳尾。一個是「大頭拖著細身」，一個是「背上扛著一整片帆」。

`lungfish` 的關鍵是 `dorsalAt` 的**起點壓到 .02**，讓背鰭一路連到尾根，跟 `fork: 0` 的圓鈍小尾扇接成一片。

**`serpent` 跟 `dragon` 的差別在哪**：兩者都是「長條形」，但

| | `dragon`（八尋） | `serpent`（耶夢加得） |
|---|---|---|
| `e` | .56（比橢圓更尖，兩端明顯收細） | **.30**（剖面接近矩形＝**粗細均勻的管子**） |
| `tailH` | .95（大尾扇） | .14（幾乎沒有尾鰭，收成一點） |
| `dorsal` | .52（長而低的背鰭，還加 `mane`） | .05（等於沒有） |

**`e` 是把「蛇」跟「帶狀魚」分開的關鍵旋鈕**：`e` 越小，`h = halfMax · s^e` 在中段越平，輪廓就越像等粗的管子。

> 附帶效果：`serpent` 的 `halfMax` 只有 5px，而胸鰭的繪製位置（`cy + profile(0.62)·0.25`）落在身體內部、被身體圖層（優先權 3 > 鰭的 1）整片蓋掉，所以**蛇身上不會冒出一片胸鰭**。這是巧合而不是設計，但結果是對的——不需要為它多開一個「不畫胸鰭」的開關。

各欄位都是**比例值**：長度類乘 `usableW`，高度類乘 `(SPR_H/2 - MARGIN) = 24`。

### 拉開輪廓差異最有效的旋鈕是 `gamma`

`gamma` 控制最寬處的位置：`t_widest = 0.5^(1/gamma)`。

- `gamma = 0.78`（pike）→ 最寬處在 t≈0.41，**在中線偏尾**，讀起來是「頭尖身後肥」的掠食型。
- `gamma = 1.70`（abyss）→ 最寬處在 t≈0.65，**明顯偏頭**，讀起來是「一顆大頭拖著細身」。

同一組配色下，把 `gamma` 從 0.78 換到 1.70 產生的差異比換 `pattern`、換整套配色都大。**要讓兩條魚看起來不一樣，先動 gamma 和 `tailH`／`fork`，最後才動顏色。**

### 吻端留白 · `headRoom`

會往吻端前方延伸的 `special` 要先預留空間，登記在一張表裡取最大值：

```js
const HEAD_ROOM = { whisker: 12, rostrum: 24, forkTongue: 12, kype: 10 };
let headRoom = 0;
for (const k in HEAD_ROOM) if (sp.indexOf(k) >= 0) headRoom = Math.max(headRoom, HEAD_ROOM[k]);

const sc = Math.min(f.scale, (0.98 - headRoom / usableW) / (S.bodyLen + S.tailLen));
const slack = usableW - total;
const xStart = Math.round(MARGIN + Math.max(0, Math.min(slack / 2, slack - headRoom)));
```

**為什麼**：鬍鬚要往前伸約 11px、劍狀長吻要 22px，但 `sc` 的夾住規則會讓魚王級的 `scale` 把吻端推到 x≈91，那些繪製碼只剩 3px 可畫。它們都有邊界檢查會自己截斷，所以**不報錯、只是靜默消失**——比報錯更難發現。原本兩位有鬍鬚的魚王都中了這個坑。

代價是這些魚整體會小 10～20%。`slack` 那一行的意思是「空間夠就置中，不夠就把留白優先讓給吻端前方」，所以**小魚（scale 小、slack 大）仍然置中**，不會因為有鬍鬚就偏左。

> **加新的往外延伸型 special，第一件事就是在 `HEAD_ROOM` 補一列。** 見 [11 §19](11-invariants-and-gotchas.md#19-吻端沒留空間鬍鬚會被切光)。

### 輪廓數學

身體是一條「半高剖面曲線」沿 x 軸掃出來的：

```js
function profile(t) {          // t: 0 = 尾根, 1 = 吻端
  tt = t ^ gamma                            // gamma 控制最寬處的位置
  s  = 1 - (2·tt - 1)²                      // 標準橢圓
  h  = halfMax · s ^ e                      // e < 0.5 → 比橢圓更飽滿
  return max(h, 1.2)   // 內部保底 1.2px，避免頭尾細到消失
}
```

- **`gamma > 1` 把最寬處往頭部推**。`gamma=1.15` 時最寬處落在 t≈0.55，符合真實魚的比例。
- **`e` 控制飽滿度**。0.5 是正橢圓，越小越接近矩形（圓胖的魚用小 e）。

尾鰭是獨立的一段，從尾根（細）往尾端（寬）張開，並在尖端挖掉一個楔形做出分叉（`fork` 控制深淺）。背鰭／臀鰭／胸鰭都用 `sin` 曲線在身體輪廓外加高度。

### 圖層優先權

用一個 `Uint8Array(W*H)` 記錄每個像素屬於什麼，數字大的覆蓋小的：

```
0 = 空 | 1 = 鰭 | 2 = 尾 | 3 = 身體
```

繪製順序：鰭 → 尾 → 身體（身體優先權最高，自然蓋住鰭根）。

### 上色

對每個身體像素算縱向位置 `v = (y - 上緣) / (2 · 半高)`，做出**反蔭蔽**（背深腹淺，真實魚的保護色）：

```
v < 0.24  → back（背色）
v < 0.40  → mix(back, body, 0.55)
v < 0.74  → body（主色）
其餘       → belly（腹色）
```

`colors` 只有 `body` 是必填，其餘會自動推導（`back = shade(body, -0.32)`、`belly = shade(body, +0.42)` 等）。想要精準控制再明寫。

> ⚠️ **`kype` 的驗證不能用「像素數有沒有變多」。** 它登記在 `HEAD_ROOM`，所以加上它會讓整條魚縮小——實測「有 kype」比「沒 kype」**少了 382 個像素**，但鉤吻其實有畫出來。正確的驗證方式是**看吻端前方的遮罩**：應該看得到一條 2px 厚、往右上斜的結構，末端高過吻端。所有登記在 `HEAD_ROOM` 的 special 都有這個問題。

新增 special 時的三條經驗：

1. **牙齒、霜晶這類細節要畫在身體像素上（覆蓋），不要往外凸。** 1px 的外凸尖刺在 4 倍放大後會被讀成雜點，而且會被描邊包起來變成一顆小黑點。
2. **弧線的取樣要夠密。** `lantern` 初版只取 11 段，步距超過 1px，竿子斷成虛線，看起來像三顆浮在頭上的點；改成 24 段才連續。
3. **細碎的點狀特徵要有形狀。** `frost` 初版是單點，跟 `pattern: 'speck'` 的雜訊完全混在一起；改成十字（中心亮、橫向兩臂用 `mix` 壓暗）才讀得出是冰晶。同理數量要少——6 顆剛好，9 顆就變成一團看不出結構的雜訊。
4. **往外長出「主要體積」的特徵不能畫成純三角形。** `rostrum` 的厚度用 `sin(u^0.55 · π)` 讓它從吻基往前先變厚（u≈0.3 最厚）再收成圓鈍的尖端。純三角形（從厚到尖線性收）會被讀成一根針，讀不出是槳狀吻板。
5. **分叉要張得夠開。** `forkTongue` 末端上下各岔 3px；只岔 1px 在 4 倍放大後看起來只是一條變粗的線，分叉的意義就沒了。
6. **special 要挑「這個輪廓缺什麼」而不是「這種生物有什麼」。** `serpent` 沒有鰭也沒有尾扇，所以它需要的是舌頭（把蛇跟鰻分開）；原本也想給它 `jaw`，但 10px 高的身體上獠牙會佔掉整個頭、反而看不出是蛇。**特徵的數量要配合輪廓的可用面積。**

### 描邊

全部畫完後掃一次，把「空的、但四鄰有實心像素」的位置塗成 `shade(back, -0.55)`。這是 4 鄰域膨脹，所以精靈實際會比輪廓大 1px——`MARGIN = 4` 就是留給它的。

`buildJunk()` 會自動算縮放（`min(96/w, 56/h) * 0.85` 取整），所以**字元圖畫多大都行**，只要長寬比不要太極端。`ice` 刻意讓左上最亮、右下最暗，在沒有光照系統的情況下用固定光源方向撐出立體感；`bone` 用「頭在左、脊椎往右、肋骨是垂直短線」的側視骨架，在 4 倍放大下才讀得出是骨頭而不是一團白點；`ema` 的上緣尖頂是繪馬的識別特徵，沒有它就只是一塊木板；`porcelain` 的缺口刻意開在**右上角而不是正中**（對稱的破損會被讀成「設計」而不是「破掉」），而且碗內的藍色紋樣要**斷開跨過缺口**，否則看起來只是一只完整的小碗；`shield` 靠**同心圓結構**（鐵緣 → 彩繪環 → 中央凸飾 → 凸飾高光）才讀得出是圓盾，少了中央那顆凸飾就只是一個圓圈——破損同樣做成不對稱（裂縫從右緣咬進去、右下角整塊缺掉）。

`ostracon` 的重點是**不規則的多邊形輪廓**（規則的方形會被讀成木板或磚，一定要缺角）加上上面幾行橫向刻痕。

後來加的四張各自有一條「不做就認不出來」的規則：`coins` 要**堆疊**（單獨一枚圓片會被讀成瓶蓋或鈕扣，三枚錯開、每枚露出側面厚度才是硬幣）；`shell` 要有**放射狀殼肋 ＋ 偏心殼頂**（少了殼肋就是一個半圓，會跟浮球混在一起）；`flask` 的**瓶頸要比瓶身窄一半以上**（等寬圓筒會被讀成鐵罐），凹陷只做右側；`brimstone` 要有**平的切面 ＋ 明顯稜線**（左上受光、右下陰影），沒有稜線的一團黃色只會被讀成海綿或麵包。

> **「破損要不對稱」這條規則已經用過四次了**（`porcelain`、`shield`、`ostracon`、`flask`）。畫新的破損類雜物直接照做，不要再從對稱開始試。

> **同類的通則**：雜物美術的辨識幾乎都卡在**一個結構特徵**上（貝殼的肋、水壺的頸、硬幣的疊、骨頭的肋排、圓盾的凸飾）。畫之前先問「拿掉哪一樣就認不出來了」，把成本花在那一樣上，其餘可以很潦草。

新增一種雜物美術：在 `JUNK_MAPS` 加一筆（`pal` + `map`），然後在 `data.js` 的魚陣列裡用 `junkArt: '新key'`。**不用改 `buildJunk()`**。

## 三 · 釣點場景

`px.drawScene(g, loc, st)`，畫布 **200×340**。

### 分層

```
靜態（有快取，buildBackground → bgCache[loc.id]）
  ├ 天空漸層（loc.scene.sky 陣列逐段內插）
  ├ ★ 地形 above()（依 loc.scene.terrain 分派，見下）
  ├ 岸線
  ├ 水面底色（waterTop → waterBot 分 5 段）
  ├ 地形倒影（把地平線以上 48 列取出、只留較暗的像素、加抖動、疊回水面）
  ├ 深水區塊（waterDeep 疊 35% 透明度）
  └ ★ 地形 below()（選用，浮冰／鳥居／發光浮游生物）

逐幀
  ├ drawSparkle()   水面反光橫線（190 條，位置由 seed 固定，隨時間左右漂移）
  ├ drawBoat()      船身／釣手／水豚／愛心／船外機／倒影（整組隨 sin 上下晃動）
  ├ drawRodAndLine()
  ├ drawFloat()     浮標（依 floatSink 下沉）
  ├ 漣漪（st.ripple）
  └ 躍出水面的魚（st.jump）
```

**背景一定要快取**：樹林要畫 230 棵、倒影要跑 `getImageData`，每幀重算會掉幀。`bgCache` 以 `loc.id` 為 key。改了 `loc.scene` 的顏色或 `terrain` 後**必須重新整理**才看得到（同 [精靈快取](#快取) 的問題）。

### 為什麼倒影用 getImageData

一開始想直接重畫一次樹林，但要對齊很麻煩。改成把已經畫好的地平線上方逐列取出、判斷亮度（`lum > 150` 就丟棄，只留暗色剪影）、乘上偏藍的係數、加水平抖動後疊回去。

這個做法在加入地形系統之後**回報更高了**：倒影不知道也不需要知道上面畫的是樹林、崖壁、冰川還是五重塔，它只是把像素往下鏡射。**所以新增一種地形完全不用寫倒影碼。**

## 三之二 · 地形系統 · `TERRAIN`

早期五個釣點共用同一套「遠山＋三層樹林」，只換調色盤——結果就是**每個釣點看起來都一樣，只是顏色不同**。地形系統就是為了解決這件事。

`loc.scene.terrain` 指定要用哪一種，`buildBackground()` 分派：

```js
const terrain = TERRAIN[P.terrain] || TERRAIN.forest;   // 沒指定就退回森林
terrain.above(T);        // 畫地平線以上
...共用的水面、倒影、深水...
if (terrain.below) terrain.below(T);   // 選用：畫在水面上的東西
```

### 目前的十二種

| key | 用在 | 畫什麼 | 關鍵手法 |
|---|---|---|---|
| `forest` | 晨霧湖 | 隨機遊走山稜 + 遠中近三層針葉林 | 原本的實作，保留為預設值 |
| `pond` | 澄澈方池 | 平草坪 + 等距樹籬球 + 筆直石砌護岸 + 木棧道，水下是帶透視的磁磚池底 | 不靠「畫什麼」，靠**線是直的**；另一半是**唯一看得見水底**的釣點，見下 |
| `cliff` | 落霞峽灣 | 兩側崖壁夾出中央水道 + 海蝕柱 | 崖高用 `pow(1-d, 1.7)` 從邊緣往中央衰減，**中間留白**才有「峽」的感覺 |
| `shrine` | 宵櫻神域 | 錐形雪山 + 五重塔 + 櫻花林 + 石燈籠，鳥居立在水上 | 雪山用**直線斜邊**（不是隨機遊走），塔的屋簷比塔身寬 |

#### 十二種地形各自佔了哪一條「辨識軸」

到第十二種為止，能用的差異手段大致被分完了。**新增第十三種之前先看這張表，挑一條還沒被佔走的軸**：

| 軸 | 誰佔了 |
|---|---|
| 天際線的**形狀** | 起伏（`forest`）／貼邊（`cliff`）／直線錐（`shrine`）／寬扁板塊（`ice`）／圓頂柱（`karst`）／幾乎空的（`night`）／**凹線**（`caldera`）／沙丘曲線（`desert`）／平的（`pond` `tidal`） |
| **單一巨物** | `yggdrasil`（樹幹）、`waterfall`（瀑布） |
| **橫向半透明帶** | `karst`（山腰霧帶） |
| **垂直半透明筆畫** | `yggdrasil`（極光，在天空）、`caldera`（蒸氣，在水面） |
| **扇形擴散** | `waterfall`（落水點水霧） |
| **人造直線／等距** | `pond` |
| **把陸地畫進水面** | `tidal` |
| **看得見水底** | `pond`（清澈見底）／`caldera`（礦物染色，但看不見底部物件） |

#### `pond` 的兩個設計決定

**一 · 人造感全部來自「線是直的」，不是來自畫了什麼。** 自然界不會出現等距、等寬、完全水平或完全垂直的東西，所以只要出現就一定被讀成人造物。這個地形把四件事疊在一起：割草機的等寬條紋、**等距等大**的樹籬球（其他地形的植被全是隨機散佈）、完全水平且每 12px 一道接縫的石砌護岸、直角的木棧道。**成本比畫一座建築低得多，辨識度卻更高**——因為它訴諸的是規律而不是造型。

**二 · 它是唯一看得見水底的釣點。** 其他十一個釣點的水都是不透明的，所以「清澈見底」本身就是識別。做法是在**已經畫好的水面上**疊一層淡的池底色（`bed`），越近越實、越遠越淡，再鋪一層帶滅點的磁磚網格（`grout`）。

> **格距一定要隨深度張開**（`step = 7 + t * 26`，縱線 `6 + t * 26`）。等距的格子會被讀成「一張貼在鏡頭上的方格紙」，張開才有往下看的透視。

實測：避開船的水面區域裡有 **2172/6286（35%）** 的像素落在池底色附近；同一段區域在晨霧湖只有 **17/6286（0.3%）**。差兩個數量級，所以「看得見底」不是錯覺。

#### `tidal` 的三個設計決定

**一 · 這是唯一一個「構圖層級」的差別。** 前十一種地形的地平線以下都是一整片水，換的只是水色。這一種把**陸地畫回水面上**：地平線往下約 80px 是裸露的灘地，只在畫面下緣留一條水道。退潮時真的會留下這樣一條深槽，所以船待在那裡是合理的——不需要為它另外解釋。

**二 · 沙紋是最便宜的紋理。** 平行、等距、微彎的波痕，一道亮的稜配一道暗的谷（各 1px）。在沒有光照系統的情況下，這兩條線就撐起了整片灘地的立體感，成本只有 13 條 `sin` 曲線。

**三 · 積水潭要「多而小」。** 每一個都要有一圈濕沙的暗邊——沒有邊的話只是灘上一塊藍色補丁。而且**尺寸放大就會被讀成水道的分支**，灘地本身就不成立了。目前是 17 個、半徑 3～9px。

> **`drawSparkle()` 每幀會在整個水面區域畫反光橫線，包括蓋在灘地上。** 這裡刻意**不修**：濕沙在退潮後本來就會反光，所以那些橫線讀起來是濕沙的光澤而不是 bug。前提是 `highlight` 要選一個在沙上與水上都成立的暖白（目前 `#fbf6ea`）。**新增「把陸地畫進水面」的地形時要記得這件事**——sparkle 是共用的，不能只為某個地形關掉。

### 場景細緻度標準（2026-08-04 起）

> **`waterfall` 是這個標準的參考實作**，其他釣點目前還是舊的細緻度，會陸續跟進。

初版的瀑布場景被打回來重畫，量化之後發現問題**不是解析度**（200×340 跟一般像素風場景圖是同一個量級），而是**資訊密度**：左半岩壁有 74% 的像素只落在兩個色階上，等於一塊平塗。新場景要過三關：

| | 要求 | 量測方式 |
|---|---|---|
| **色階** | 每一層材質展開成**六階明度**，再用 4×4 Bayer 有序抖動補中間調 | 地平線以上的色數 ≥ 600；最大兩個色階的合計佔比 < 60% |
| **植被** | 樹冠框上緣、平台長灌木、少量垂藤 | 綠色像素佔地平線以上 ≥ 15% |
| **光** | 逆光光暈（先畫、被地形蓋掉、只從缺口透出）＋ 寬而淡的斜射光束 | 目視 |

**單顆石頭的三件事**（少一件就會糊成麻點）：上亮下暗的縱向分層、**只有左半**的頂緣高光（整圈都亮會變成球）、底部一道接觸陰影讓它「坐」在後面的岩上。

> ⚠️ **背景有 `bgCache`，一個釣點一輩子只跑一次**，所以細緻度幾乎不花錢——初版的 80 行變成 350 行，幀率完全沒動。**不要為了效能省這裡的筆數。**

#### 規則的圖案不像自然物（重畫時踩到的三個坑）

| 症狀 | 原因 | 對策 |
|---|---|---|
| 落水點像一張**射箭靶紙** | 畫了一圈圈**完整**的同心橢圓 | 改成隨機半徑的**弧段**，每段各自抖動 |
| 瀑布像**白色水管** | 寬度是常數 | 寬度隨高度變化：頂端收窄、往下散開，再疊兩個不同頻率的起伏 |
| 垂藤像**一排綠色的蟲** | 每個平台掛五六條、長度都差不多 | 一個平台一到兩條，長度差距拉到三倍 |

**通則：自然界沒有等距、等寬、完整的同心圓。** 這條跟 `pond` 那邊反過來用是同一件事——那裡刻意用等距直線表達「人造」，所以這裡只要出現規則圖案就會被讀成人工物。

#### `waterfall` 的三個設計決定

**一 · 跟 `cliff` 刻意做成鏡像。** `cliff` 是兩側暗崖夾出中央的亮縫；這裡是整面暗岩被一道亮柱切開。同一個「亮暗對比」的構圖翻過來用，成本為零，而且兩者放在一起不會認錯。岩壁用**水平**層理（`cliff` 是**垂直**節理），這是第二道保險。

**二 · 亮柱必須跟 `yggdrasil` 的樹幹分開，靠三件事。** 兩者都是「一根貫穿畫面的直立物」：

1. **顏色是全畫面最亮的**（實測瀑柱亮度 234 vs 岩壁 62）。
2. **有橫向流束**——每隔幾列一道較暗的橫紋。樹幹是縱向紋理，這一條就把「在流」跟「站著」分開了。
3. **底部有水霧**，樹幹沒有底。

> **細瀑一定要 2px 以上。** 1px 的垂直線在這個尺寸一律被讀成雨絲（冰川裂隙踩過同一個坑）。目前三道瀑布是 24 / 8 / 5px。

**三 · 水霧做成往上擴散的扇形，刻意不用橫帶。** 橫帶是 `karst` 山腰霧帶的招牌，撞上去等於白做一種地形。扇形的做法是從落水點往上逐列加寬（`spread = 15 + k * 1.5`）並讓 alpha 遞減——這也剛好是水花真實的行為。

#### `caldera` 的三個設計決定

**一 · 凹的天際線是最後一種還沒被用掉的天際線形狀。** 前十一種不是起伏（`forest` `desert`）就是往上長的東西（塔峰、樹幹、金字塔、雪山）。**兩側高、中間低**的凹曲線（`h = 11 + pow(d, 1.6) * 54`）直接說明「你站在一個坑裡面」，一行公式就講完，不需要任何細節。

**二 · 火山錐是尖三角的高風險輪廓，靠平頂救回來。** [§16](11-invariants-and-gotchas.md#16-尖三角剪影一律會被讀成針葉樹) 說這個尺寸下尖三角一律被讀成針葉樹。金字塔的解法是「左右明暗分明」，這裡用的是另外兩件事：**把頂削平**（截頭錐＝火口），加上**從平頂接一根往上加寬的煙柱**。針葉樹沒有平頂，更沒有煙。

**三 · 硫磺階地是全畫面唯一貼著岸線的亮色。** 五道帶狀的黃白結晶疊在水線上方，`sin` 讓每一道的高度起伏。它遠亮於倒影的門檻（150），所以水裡不會有它的影子——跟 `karst` 的白牆同一個理由，刻意接受。

> **水面蒸氣要成塊分佈，不能滿版。** 滿版的垂直筆畫是 `yggdrasil` 極光的做法。這裡用 11 團、各自有寬度與高度的汽柱，而且畫在**水面**（極光畫在天空）——位置與分佈兩件事都不同，才不會被看成「水裡也有極光」。

#### `desert` 的三個設計決定

**一 · 金字塔是「尖三角」的高風險輪廓，靠三件事救回來。** [§16](11-invariants-and-gotchas.md#16-尖三角剪影一律會被讀成針葉樹) 說這個尺寸下尖三角一律會被讀成針葉樹。金字塔避開的方法是：

1. **尺寸夠大**（72×44，是針葉樹的四倍）。
2. **垂直中線一分為二，左受光右陰影**——樹沒有這個。實測同一列的亮面／暗面像素數應該對稱（37/32、28/29、23/24、19/19…）。
3. **底邊坐在平坦的沙帶上**，而不是插在起伏的林線裡。

另外每 6 列疊一道稍暗的橫線當層階，讓斜面不是一片死板的平塗。

**二 · 沙丘一定要有「保底沙帶」。** 沙丘是 `sin` 疊半頻 `sin` 畫的（不對稱稜線＝迎風面長、背風面陡），但**波谷的高度會趨近 0**，只靠曲線的話波谷處會露出一條天空色的縫。初版就是這樣，地平線上方多了一條 10px 的假天空。

```js
rect(0, horizon - 17, W, 21, P.midTree);   // 先鋪實心沙帶，再把沙丘畫在上面
```

上緣必須蓋過**遠沙丘的 `baseY`**，否則波谷還是會從遠沙丘與近沙丘之間漏出來。

**三 · 繪製順序就是景深順序。** `遠沙丘 → 金字塔 → 方尖碑 → 近沙丘 → 棕櫚`。近沙丘要**最後**才畫，才能把金字塔與方尖碑的底部遮住；反過來的話那些建築會像浮在沙丘上面。

`below()` 的石柱要有**比柱身寬的柱頭**才讀得出是柱子而不是木樁；紙莎草的基部 `y` 要夠低，因為花序在 `y - h`，設得離岸線太近的話花序會長到地平線**上面**去（初版就是這樣，紙莎草長在沙丘上）。

#### `yggdrasil` 的三個設計決定

**一 · 構圖改成「單一巨物」。** 前六種地形都是「很多個小東西排開」（樹林、崖壁、冰脊、塔峰、海蝕柱）。這一種反過來：一根樹幹佔掉畫面寬度的兩成以上、從水面貫穿到畫面頂端，樹冠與粗枝**刻意畫到畫面外**，用「裝不下」表達尺度。在 200×340 的畫布上，這是最省力也最強的辨識手段——不需要任何細節，光是輪廓就跟其他六種完全不同。

樹幹位置固定在 `tx = 38`（偏左），把中央水道留給船與兩個浮標。樹幹只畫到地平線；水面以下由**倒影**接手（倒影會自動把樹幹往下鏡射，所以看起來就是從水裡長出來的），另外在 `below()` 畫三道拱出水面的樹根。

**二 · 極光是垂直的簾子，不是橫帶。** 做法：先算一條 `sin` 疊 `sin` 的下緣，再從下緣**往上**畫垂直筆畫、alpha 隨高度衰減；每 3px 一道較亮的筆畫，筆畫之間的明暗差就是簾子的褶皺。

**刻意不用橫帶**——那會撞到 `karst` 的山腰霧帶。

> ⚠️ **兩道簾子的 base 要拉開 40px 以上。** 初版只差 30px、高度又設 34/46，兩道完全疊在一起，青綠與紫糊成一團看不出是兩層。改成 `base = horizon - 22 - b*40`、高度 30/34 之後才分開。驗證方式是逐列統計 R/G/B 對「純天空漸層」的偏離量：**紫簾子的區間 B 大於 G，青綠簾子的區間 G 大於 B，中間要有一段接近零的間隙。**

**三 · 符文石要微微傾斜。** 立正的石板看起來像柱子，歪一點（`lean` 0.08～0.2）才像「被人立起來很久了」。刻痕用橫向短線加偶爾一道豎筆，構成「讀不懂但有規律」的字樣——**不要真的去拼北歐字母**，那個尺寸下拼出來也認不出，反而會變成雜點。

#### `karst` 的三個設計決定

**一 · 塔峰的輪廓：垂直側壁 + 半圓頂。** 側壁往上只內收 18%（`half = w*0.5*(0.82 + t*0.18)`），頂部用半圓收頭。這是為了不撞到既有地形——`shrine` 的錐山是「從頂點線性往下張開」，`forest` 的針葉樹是三角形，`night` 的海蝕柱是矮胖矩形，`cliff` 的崖壁貼著畫面邊緣。實測驗證方式是量同一根塔在不同高度的寬度：**前 9 列從 10 迅速張到 25（圓頂），之後 20 列維持 19～25（垂直壁）**。錐形則會一路線性變寬。

**二 · 橫向霧帶才是「中國山水」的來源。** 三條半透明白色橫帶，越靠峰腳越厚越白（霧積在谷底）：

```js
[[0.30, 7, 0.34], [0.52, 6, 0.24], [0.74, 4, 0.15]]   // [峰高比例, 厚度px, 最大不透明度]
```

把峰群橫切成上下數截，遠近立刻分開。**這是全六種地形裡唯一用橫條的**，也是最省成本的辨識手段：只要三次半透明 `fillRect`，比再畫一層山便宜得多。厚度用 `sin` 加權讓帶緣自然淡出，硬邊會變成一條膠帶。

**三 · 月拱橋畫在 `below()`。** 半圓弧是全遊戲唯一的圓弧輪廓，辨識度最高。它必須在 `below()` 才不會被水面／倒影／深水的半透明疊層洗掉。**荷葉要畫在橋之前**，橋才會像實體壓在葉子上；反過來葉子會浮在橋面上。位置固定在 `cx=158`，避開船（x 40～150、y 216～268）與兩個浮標位置。

### `above(T)` / `below(T)` 拿到的上下文

```js
T = { g, P, R, W, H, horizon, rect, forest }
```

- `P` = `loc.scene`；`R` = 以 `loc.seed` 起始的亂數（**同一個釣點每次長一樣**）
- `rect(x, y, w, h, color)` — 已經幫你做好取整
- `T.forest(baseY, height, color, density, accent)` — 針葉林產生器，任何地形都可以叫

**`below()` 在水面、倒影、深水全部畫完之後才跑**，所以它畫的東西不會被那些半透明疊層洗掉。代價是它得自己處理倒影（`shrine` 的鳥居就是自己鏡射的，靠「R 通道明顯大於 B」把朱色挑出來）。

### 兩個踩過的坑

1. **尖三角在這個尺寸下一律會被讀成針葉樹。** 冰脊初版用三角錐畫，成品跟晨霧湖的樹林幾乎分不出來，等於白做。改成「寬 ≫ 高、頂面是平的」的斜面板塊之後才像冰。**新增地形時，先問自己這個輪廓會不會撞到既有地形。**
2. **從高處往下垂的細線會被讀成雨絲。** 冰川的裂隙初版是從頂端往下畫，看起來像下雨。改成從底部往上長、長度縮短就正常了。

### 新增一種地形

1. `pixel.js › TERRAIN` 加一筆 `{ above, below? }`。
2. `data.js` 的釣點 `scene` 加 `terrain: '新key'`，以及該地形需要的自訂色（例如 `shrine` 用 `snow` `pagoda` `torii`，`ice` 用 `floe`，`night` 用 `star` `plankton`）。
3. **`px.locThumb()` 的 `switch (P.terrain)` 也要補一個 case**，否則釣點選單的縮圖會退回預設的樹林，跟場景對不起來。縮圖刻意不共用 `TERRAIN`——尺寸差 3 倍以上，等比縮放的細節會糊掉，簡化版反而好認。
4. 改完**重新整理**（`bgCache`）。

## 四 · 家園房間

`px.drawRoom(g, st)`，畫布 **200×150**，**回傳 `{ tank: {x, y, w, h} }`** 讓呼叫端知道魚缸的範圍。

```js
st = { time, tankLevel, deco, poster }
```

- 牆（直條紋壁紙）、地板（木紋）、窗戶（看得到湖景）
- **掛畫**：`st.poster` 是一張 canvas，由 `screen-home.js` 用 `px.locThumb(loc, 60, 40)` 產生並快取（`_posterLoc` 記錄目前是哪個釣點）
- **魚缸**：尺寸隨 `tankLevel` 成長（`76 + (lv-1)*12` 寬、`52 + (lv-1)*5` 高），內含水色漸層、光紋、底砂、會搖擺的水草、玻璃外框
- 裝飾：`rug` `plant` `trophy` `cat` `neon` `lamp` `shishi` `shellrack` `cascade` `onsen` `sarco`，各自是一段 `if (deco.xxx)` 的繪製碼。
  `sarco`（彩繪石棺）的識別重點是**頂端的面具臉**（眼＋假鬍）——少了它就只是一塊直立的木板；
  `shishi`（竹添水）靠**傾斜的竹筒 + 底下的承石**，而且**必須會動**（週期性傾倒），靜態的話就是一根斜靠在牆邊的棍子；
  `shellrack`（貝殼標本架）的三層層板上要放**三種不同形狀**的貝（塔螺／扇貝／芋螺），全畫成半圓的話只是三排小丘；
  `cascade`（循環水景）的水柱橫紋要**每幀往下捲**，不然只是兩個盆子中間一條白線；
  `onsen`（檜木泡湯桶）要有**桶箍**（兩道深色橫帶）才讀得出是木桶，桶口的蒸氣是它跟盆栽分開的地方

> **有三件裝飾是「靠動作定義的物件」**（`shishi` `cascade` `onsen`）。這類東西的動畫不是加分項而是**識別的必要條件**，因為它們的靜態剪影跟別的家具沒有差別。加同類裝飾時要一併想好它要怎麼動。
- 睡覺的水豚＋呼吸泡泡

魚缸裡游動的魚**不在 `drawRoom` 裡畫**，是 `screen-home.js › frame()` 拿到回傳的 `tank` 矩形後，自己 clip 並用 `px.drawSprite()` 畫上去。游動狀態存在 `S.swimmers[uid]`，每幀更新 x 位置、碰到邊界轉向，y 加 sin 擺動。

新增裝飾要動兩處：`drawRoom()` 加繪製碼、`screen-home.js › DECO_ART` 加圖示，外加 `data.js › FG.DECOS` 加資料。

## 五 · 地點縮圖

`px.locThumb(loc, w, h)` — 簡化版場景（天空漸層＋**依 `terrain` 分派的剪影**＋水面反光），任意尺寸。加新地形記得補這裡的 `switch` case。用在釣點選單、每日分頁的釣點卡、家園牆上的掛畫。**沒有快取**，呼叫端要自己存起來（家園就是這樣做的）。
