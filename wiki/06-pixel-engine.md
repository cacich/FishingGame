# 06 · 像素引擎

> 涵蓋：`js/pixel.js`（約 4900 行，全專案最大的檔案）
> 相關：[07 資料規格](07-data-schema.md)（魚的欄位）、[09 操作手冊](09-recipes.md)

魚、圖示、房間與全部地形仍由 canvas 在低解析度上逐像素畫出來，再交給 CSS `image-rendering: pixelated` 整數放大。釣點場景另外支援**選用的點陣底圖**，船上的木船／坐姿釣手／狗則使用十二格點陣序列圖；兩者載入失敗都保留程序化備援，因此外部產圖不會變成啟動或離線可玩的單點故障。

## 五種產圖方式

| 方式 | 用途 | 入口 |
|---|---|---|
| **字元圖**（char map） | 固定造型的小物：介面圖示、雜物、角色備援、家園水豚、裝備／裝飾圖示 | `px.drawMap()` |
| **程序化生成** | 魚：由參數算出輪廓與上色 | `px.sprite()` → `buildFish()` |
| **參數化繪製** | 場景：釣點風景、家園房間、地點縮圖 | `px.drawScene()` / `drawRoom()` / `locThumb()` |
| **點陣場景資產** | 選用的釣點靜態背景與橫式縮圖 | `scene.art` → `loadImage()`；失敗時退回參數化繪製 |
| **點陣角色序列** | 船上的木船、釣手與狗待機循環 | `assets/characters/fishing-idle.png` → `drawBoat()`；失敗時退回字元圖＋程序化船 |

## 基礎工具

```js
px.make(w, h)                          // 建立 canvas，關掉 smoothing
px.drawMap(ctx, map, pal, ox, oy, s)   // 畫字元圖
px.mapSize(map)                        // 回 { w, h }
px.hashStr(s)                          // FNV-1a，把 id 轉成穩定的數字種子
```

## 一 · 字元圖

用字串陣列描述圖案，一個字元一像素，配一張 `{ 字元: 色碼 }` 調色盤。**點（`.`）或不在調色盤裡的字元 = 透明**。

```js
const HEART = {
  pal: { r: '#e2555f', l: '#f18c93' },
  map: [
    '.rr.rr.',
    'rlrrrrr',
    'rrrrrrr',
    '.rrrrr.',
    '..rrr..',
    '...r...'
  ]
};
px.drawMap(ctx, HEART.map, HEART.pal, x, y, 1);
```

## 二 · 程序化魚類生成

`buildFish(f)` 是全檔最複雜的函式。輸入一筆魚的資料定義，輸出一張面向右的像素精靈。

### 畫布規格

```js
SPR_W = 96, SPR_H = 56, MARGIN = 4     // 所有魚共用同一張畫布尺寸
usableW = 96 - 8 = 88
```

**所有魚都畫在同尺寸畫布上**，體型差異靠 `scale` 參數控制佔比。這樣圖鑑格子、結果卡、魚缸裡並排時，大魚看起來就是比較大隻，不需要額外處理縮放。

```js
sc = min(f.scale, 0.98 / (S.bodyLen + S.tailLen))   // 夾住，避免撐出畫面
```

| `ray` | .36 | .03 | .00 | 一根鞭子（不是尾扇） |

`wrasse` 的 `tailH .74` 比前三者小一截，所以就算 `fork` 跟 `koi` 只差 .06 也不會混——`koi` 的尾巴佔掉體長三成、高度是身體的 1.18 倍，那是一整片拖在後面的紗；`wrasse` 是一把短而挺的扇子。

**`octopus` 為什麼是一個圓**：`gamma 1.00` ＋ `e .50` 就是**標準橢圓**（見下方輪廓數學），而 `bodyLen .42 × usableW = 37px` 與 `2 × halfMax = 2 × 24 × .74 = 36px` 幾乎相等——所以那個橢圓是一個圓。這是全部輪廓裡唯一刻意畫成圓的，也是「圓圓的太陽升起」這個名字的來源。**只有輪廓不夠**：一顆圓球加上尾鰭會被讀成河魨，所以 `tailH .08` / `dorsal .04` 把鰭全部關掉，識別交給 `arms`（八條腕）與 `slitEye`（水平長瞳）。

**`coelacanth` 怎麼跟 `catfish` 分開**：兩者都是粗壯的中型身。差別在 `gamma`——`catfish` 1.42 把最寬處推到 t≈0.61（大頭收尾），`coelacanth` 1.02 讓最寬處落在 t≈0.51，**是二十種魚王輪廓裡唯一「正中央最寬」的**。配上 `e .36` 的方剖面，讀起來就是一個兩端一樣粗的木桶，而不是一顆頭拖著身體。

**`skipper` 怎麼跟 `abyss` 分開**：兩者的 `gamma` 都偏大（大頭）。差別在背鰭與尾巴——`abyss` 是 `dorsal .24` ＋ `tailH .48` 的小尾，`skipper` 是 `dorsal .70`（**全檔最大**）從 `.08` 一路鋪到 `.78`，加上完全不分叉的圓槳尾。一個是「大頭拖著細身」，一個是「背上扛著一整片帆」。

`lungfish` 的關鍵是 `dorsalAt` 的**起點壓到 .02**，讓背鰭一路連到尾根，跟 `fork: 0` 的圓鈍小尾扇接成一片。

**`serpent` 跟 `dragon` 的差別在哪**：兩者都是「長條形」，但

| | `dragon`（八尋） | `serpent`（耶夢加得） |
|---|---|---|
| `e` | .56（比橢圓更尖，兩端明顯收細） | **.30**（剖面接近矩形＝**粗細均勻的管子**） |
| `tailH` | .95（大尾扇） | .14（幾乎沒有尾鰭，收成一點） |
| `dorsal` | .52（長而低的背鰭，還加 `mane`） | .05（等於沒有） |

**`e` 是把「蛇」跟「帶狀魚」分開的關鍵旋鈕**：`e` 越小，`h = halfMax · s^e` 在中段越平，輪廓就越像等粗的管子。

> 附帶效果：`serpent` 的 `halfMax` 只有 5px，而胸鰭的繪製位置（`cy + profile(0.62)·0.25`）落在身體內部、被身體圖層（優先權 3 > 鰭的 1）整片蓋掉，所以**蛇身上不會冒出一片胸鰭**。這是巧合而不是設計，但結果是對的——不需要為它多開一個「不畫胸鰭」的開關。

各欄位都是**比例值**：長度類乘 `usableW`，高度類乘 `(SPR_H/2 - MARGIN) = 24`。

### 拉開輪廓差異最有效的旋鈕是 `gamma`

`gamma` 控制最寬處的位置：`t_widest = 0.5^(1/gamma)`。

- `gamma = 0.78`（pike）→ 最寬處在 t≈0.41，**在中線偏尾**，讀起來是「頭尖身後肥」的掠食型。
- `gamma = 1.70`（abyss）→ 最寬處在 t≈0.65，**明顯偏頭**，讀起來是「一顆大頭拖著細身」。

同一組配色下，把 `gamma` 從 0.78 換到 1.70 產生的差異比換 `pattern`、換整套配色都大。**要讓兩條魚看起來不一樣，先動 gamma 和 `tailH`／`fork`，最後才動顏色。**

### 吻端留白 · `headRoom`

會往吻端前方延伸的 `special` 要先預留空間，登記在一張表裡取最大值：

```js
const HEAD_ROOM = { whisker: 12, rostrum: 24, forkTongue: 12, kype: 10 };
let headRoom = 0;
for (const k in HEAD_ROOM) if (sp.indexOf(k) >= 0) headRoom = Math.max(headRoom, HEAD_ROOM[k]);

const sc = Math.min(f.scale, (0.98 - headRoom / usableW) / (S.bodyLen + S.tailLen));
const slack = usableW - total;
const xStart = Math.round(MARGIN + Math.max(0, Math.min(slack / 2, slack - headRoom)));
```

**為什麼**：鬍鬚要往前伸約 11px、劍狀長吻要 22px，但 `sc` 的夾住規則會讓魚王級的 `scale` 把吻端推到 x≈91，那些繪製碼只剩 3px 可畫。它們都有邊界檢查會自己截斷，所以**不報錯、只是靜默消失**——比報錯更難發現。原本兩位有鬍鬚的魚王都中了這個坑。

代價是這些魚整體會小 10～20%。`slack` 那一行的意思是「空間夠就置中，不夠就把留白優先讓給吻端前方」，所以**小魚（scale 小、slack 大）仍然置中**，不會因為有鬍鬚就偏左。

> **加新的往外延伸型 special，第一件事就是在 `HEAD_ROOM` 補一列。** 見 [11 §19](11-invariants-and-gotchas.md#19-吻端沒留空間鬍鬚會被切光)。

### 輪廓數學

身體是一條「半高剖面曲線」沿 x 軸掃出來的：

```js
function profile(t) {          // t: 0 = 尾根, 1 = 吻端
  tt = t ^ gamma                            // gamma 控制最寬處的位置
  s  = 1 - (2·tt - 1)²                      // 標準橢圓
  h  = halfMax · s ^ e                      // e < 0.5 → 比橢圓更飽滿
  return max(h, 1.2)   // 內部保底 1.2px，避免頭尾細到消失
}
```

- **`gamma > 1` 把最寬處往頭部推**。`gamma=1.15` 時最寬處落在 t≈0.55，符合真實魚的比例。
- **`e` 控制飽滿度**。0.5 是正橢圓，越小越接近矩形（圓胖的魚用小 e）。

尾鰭是獨立的一段，從尾根（細）往尾端（寬）張開，並在尖端挖掉一個楔形做出分叉（`fork` 控制深淺）。背鰭／臀鰭／胸鰭都用 `sin` 曲線在身體輪廓外加高度。

### 圖層優先權

用一個 `Uint8Array(W*H)` 記錄每個像素屬於什麼，數字大的覆蓋小的：

```
0 = 空 | 1 = 鰭 | 2 = 尾 | 3 = 身體
```

繪製順序：鰭 → 尾 → 身體（身體優先權最高，自然蓋住鰭根）。

### 上色

對每個身體像素算縱向位置 `v = (y - 上緣) / (2 · 半高)`，做出**反蔭蔽**（背深腹淺，真實魚的保護色）：

```
v < 0.24  → back（背色）
v < 0.40  → mix(back, body, 0.55)
v < 0.74  → body（主色）
其餘       → belly（腹色）
```

`colors` 只有 `body` 是必填，其餘會自動推導（`back = shade(body, -0.32)`、`belly = shade(body, +0.42)` 等）。想要精準控制再明寫。

### 花紋 · `pattern`

| 值 | 效果 |
|---|---|
| `none` / 省略 | 只有反蔭蔽 |
| `stripe` | 垂直條紋（每 8px 畫 2px） |
| `band` | 一條側線橫帶（v≈0.46） |
| `band2` | 兩條橫帶（v≈0.40 與 0.62） |
| `spot` | 隨機斑點，位置由 `FG.seeded(hash(id))` 決定 → **同一條魚每次生成都一樣** |
| `speck` | 細碎點狀，用 `(x·7 + y·13) % 11` 的確定性雜訊 |
| `net` | 網格 |
| `scale` | 鱗片交錯紋 |
| `gradient` | 沿 `t`（尾到頭）連續變色，用 `FG.mix(c, patC, t * 0.6)`——跟其餘七種都是「重複紋理」或「帶狀」不同，這是唯一連續漸變的 |
| `saddle` | 背側鞍斑：只長在背部（`v < 0.38`）的等距色塊（`Math.floor(t * 4.5) % 2`），到不了腹部，跟 `stripe`（貫穿全身高）的差別在此 |
| `ocellus` | 尾柄假眼：固定在 `t≈0.18` 的單一同心圓（深色瞳＋淺色圈），是全部花紋裡唯一的「單一標記」，其餘都是重複或帶狀 |
| `chevron` | 人字紋：沿身體重複的 V 形斜紋（`bandV` 隨 `t % 0.16` 的鋸齒波），跟 `stripe`（垂直直條）在幾何上是「斜的」對「直的」 |

> **2026-08-06 補的這四種**，原因是原本八種裡六種是「重複紋理」（`stripe`/`spot`/`speck`/`net`/`scale` 都是雜訊或週期性重複，`band`/`band2` 是橫帶），花色手法過於集中，同釣點同階級的魚很容易撞到同一種讀感（`none` 一度佔非魚王魚的 26%）。新四種刻意各佔一種前八種沒有的幾何邏輯：連續漸變（`gradient`）、只在背部的分段色塊（`saddle`）、單一固定標記（`ocellus`）、斜向鋸齒（`chevron`）。實作都在 `pixel.js` 的 `switch (f.pattern)` 裡，直接讀 `t`（沿身體長度 0～1）與 `v`（沿身體高度 0～1，已經算好的反蔭蔽位置），不用額外傳參數。

> ⚠️ **`kype` 的驗證不能用「像素數有沒有變多」。** 它登記在 `HEAD_ROOM`，所以加上它會讓整條魚縮小——實測「有 kype」比「沒 kype」**少了 382 個像素**，但鉤吻其實有畫出來。正確的驗證方式是**看吻端前方的遮罩**：應該看得到一條 2px 厚、往右上斜的結構，末端高過吻端。所有登記在 `HEAD_ROOM` 的 special 都有這個問題。

`arms` 的三條規則（少一條就變成水母）：**基部粗末端細而且要捲**（等寬的直線是觸手）、**要有吸盤**（腕跟觸手唯一的分界）、**遠側的四條要壓暗**（八條同色會糊成一片扇形，跟 `limbs` 同一個道理）。

> ⚠️ **`arms` 的取樣密度踩過 `lantern` 同一個坑。** 初版一格一格畫（步距 0.92px），末端急彎處 y 一次跳兩三格，八條腕全部斷成虛線。現在是**步距 0.46px ＋ 每一步把上一個取樣點的 y 補起來**，另外把蜿蜒的振幅往末端收掉（`× (1 − u·0.75)`），否則 1px 寬的腕尖會散成幾顆孤立的點。驗證方式是印 ASCII 遮罩看腕有沒有斷，不要看畫面。

新增 special 時的三條經驗：

1. **牙齒、霜晶這類細節要畫在身體像素上（覆蓋），不要往外凸。** 1px 的外凸尖刺在 4 倍放大後會被讀成雜點，而且會被描邊包起來變成一顆小黑點。
2. **弧線的取樣要夠密。** `lantern` 初版只取 11 段，步距超過 1px，竿子斷成虛線，看起來像三顆浮在頭上的點；改成 24 段才連續。
3. **細碎的點狀特徵要有形狀。** `frost` 初版是單點，跟 `pattern: 'speck'` 的雜訊完全混在一起；改成十字（中心亮、橫向兩臂用 `mix` 壓暗）才讀得出是冰晶。同理數量要少——6 顆剛好，9 顆就變成一團看不出結構的雜訊。
4. **往外長出「主要體積」的特徵不能畫成純三角形。** `rostrum` 的厚度用 `sin(u^0.55 · π)` 讓它從吻基往前先變厚（u≈0.3 最厚）再收成圓鈍的尖端。純三角形（從厚到尖線性收）會被讀成一根針，讀不出是槳狀吻板。
5. **分叉要張得夠開。** `forkTongue` 末端上下各岔 3px；只岔 1px 在 4 倍放大後看起來只是一條變粗的線，分叉的意義就沒了。
6. **special 要挑「這個輪廓缺什麼」而不是「這種生物有什麼」。** `serpent` 沒有鰭也沒有尾扇，所以它需要的是舌頭（把蛇跟鰻分開）；原本也想給它 `jaw`，但 10px 高的身體上獠牙會佔掉整個頭、反而看不出是蛇。**特徵的數量要配合輪廓的可用面積。**
7. **往外長的特徵，配色跟身體太接近就等於沒畫。** `sucker` 初版用 `mix(body, belly, 0.55)`、`hump` 初版用 `shade(back, 0.14)`，兩個都跟身體差不到一階，成品一個像潛艇、一個看不出額頭有東西。改成明確的淺色（`#d8d0ac` / `#7fe8d0`）之後才讀得出來。**驗證方法是把精靈放到 4 倍，如果要瞇著眼才找得到那個特徵，就是配色不夠。**
8. **凸出去的量要夠。** `sucker` 初版只伸到 1.75 倍半高，跟腹部連成一塊，那條關鍵的水平底緣根本沒機會被看見；改成 2.4 倍才明顯低於身體最寬處。`hump` 同理，0.5 → 0.62。

### 描邊

全部畫完後掃一次，把「空的、但四鄰有實心像素」的位置塗成 `shade(back, -0.55)`。這是 4 鄰域膨脹，所以精靈實際會比輪廓大 1px——`MARGIN = 4` 就是留給它的。

### 快取

```js
px.sprite(f)   // fishCache[f.id]，第一次生成後永久快取
```

> ⚠️ **快取的 key 只有 `f.id`。** 改了某條魚的顏色／體型後，同一個 session 內不會重繪，必須重新整理頁面。除錯時很容易被騙。見 [11 地雷](11-invariants-and-gotchas.md#3-精靈快取)。

### 選用的 AI 產圖精靈 · `EXTERNAL_SPRITES`

`pixel.js › EXTERNAL_SPRITES` 會在第一次需要精靈圖時，從已載入的 `FG.LOCATIONS` 自動建立覆寫表。二十張地圖的 463 個可釣項目全部都有 `assets/sprites/<location id kebab-case>/<fish id>.png` 正式美術。每張 PNG 都已去背並固定成 96×56 RGBA，故能與程序化精靈使用同一套 `drawSprite()`／`spriteEl()` 排版。自動覆寫表仍會為新 id 推導路徑，缺檔只會保留程序化版本，不會留下空白；但這個容錯只供載入失敗與舊快取備援，**新增釣點不能把缺少正式 PNG 當作完成狀態**。

不用手寫數百筆路徑，是為了讓資料表新增釣點或魚種時自然遵循同一個命名契約。索引延後至第一次 `requestExternalSprite()` 才建立，因為 `pixel.js` 的載入順序早於 `data.js`；這避免啟動時讀取未定義的 `FG.LOCATIONS` 而中斷整個畫面。`requestExternalSprite()` 仍會先建立程序化版本，外部圖缺檔或載入失敗時便維持備援畫面，離線與 `file://` 不會出現空白精靈。

`px.sprite()` 第一次被呼叫時仍會先同步建立程序化精靈；若該 id 在覆寫表中，則非同步載入 PNG，成功後以同一個 `fishCache[f.id]` 取代。這是刻意的**漸進式覆寫**：首幀、離線、`file://` 或缺圖時不會白掉，圖片到位後的後續繪製才改用正式美術。`px.spriteEl()` 也會訂閱同一張圖片的載入完成事件，直接重畫已插入 DOM 的 canvas；因此首次開啟圖鑑、結果卡或家園清單不需要切頁重建才能看到正式圖。`pixel.js › loadImage()` 會為 `assets/` 圖片附加 `IMAGE_REVISION` 查詢參數，讓仍由舊 Service Worker 控制的頁面也會把改版圖片當成新請求；新版 `sw.js` 以 `ignoreSearch` 命中無 query 的預快取檔，離線時仍只需要同一份資產。每次替換圖片時，`IMAGE_REVISION` 與 SW `VERSION` 必須一起提升；新增下一批時，檔案、覆寫表與 `sw.js › ASSETS` 也必須一起補。

> **朝向契約**：所有魚類 PNG 的原始朝向必須是**魚頭朝右**，才能和 `buildFish()`、`px.drawSprite()` 的 `flip` 語意一致；雜物不套用這條規則。若只需修正已完成的產圖朝向，使用 `tools/flip-sprites.py` 對資料表中非 `junkArt` 的魚類路徑做水平鏡像，切勿重新產圖或翻轉晨霧湖已正確的檔案。

朱楓天守、雪見狐湯、劍影寒潭與敦煌月泉的新增精靈都以 3×4 規格表產出，再由 `tools/split-sprite-sheet.py` 按固定 row-major 名單縮進 96×56 RGBA 畫布。一般模式只適用於已確認主體完全留在格內的母版，會按幾何格線裁切並保留最大 8 鄰接主體；只要頭尾、鰭鬚或特效可能越線，就必須先以 ImageGen 技能的 `remove_chroma_key.py --soft-matte --despill` 產出乾淨 RGBA 母版，再加 `--component-cells`，讓工具依完整母版的連通元件重心歸屬格位。後者會保留跨格的完整主體，也不會把上、下或左右相鄰格的主體碎片一起縮入成品。兩張和風地圖的 47 張與兩張中國風地圖的 46 張都已按這條完整母版流程重切。

純鍵色容差只能刪掉接近 `#FF00FF` 的背景，無法處理由反鋸齒形成的紫色混邊，也無法分辨 ImageGen 真正畫進主體最外圈的 lavender／fuchsia glow。工具因此有兩層去紫邊：`despill_key_fringe()` 只追蹤「能沿接近鍵色像素走到透明區」的污染帶，以最近的非污染主體色由內向外填回；`clean_purple_outer_edge()` 再只重著色最外圈一像素的高亮紫／桃紅。前者不碰封閉在魚身內的合法紫色，後者不碰內部花紋，兩者都保持 alpha mask 不變，避免清邊時削短鬚、細鰭或長綾。

產圖規格必須使用精確 `#FF00FF` 純色背景、每格一個主體，並禁止輪廓外光暈／半透明 bloom；發光效果留在主體內或用緊貼輪廓的實色像素。`split-sprite-sheet.py › despill_key_fringe()` 先修鍵色混邊，`clean_colored_outer_glow()` 在母版縮小前處理 3～6px 厚、**不限定色相**的模型外光，`normalize_outer_outline()` 再把成品彩色最外圈轉成由內側色衍生的暗描邊；三者都保留 alpha 輪廓，避免清邊時削短細鰭與鬚。最大連通元件清理能移除孤立殘點，不能修復已被幾何裁切砍掉的像素；因此不能只看母版或尺寸檢查。正式驗收要把整站成品排成**遊戲同款深色底 4 倍** contact sheet，逐張確認頭、尾、鰭、鬚與特效都完整，沒有相鄰格碎片、洋紅鍵色殘留，或青、藍、粉、紫等任何色相的外光；同時由腳本確認檔案數、96×56 RGBA、透明與不透明像素、安全留白、魚頭朝右、近鍵色外緣為 0，且最外圈沒有高彩度亮色像素。合法的蒸氣、鬚或裝飾可能是分離元件，不可用「只能有一個連通元件」取代視覺驗收。最後將每張圖列入 `sw.js › ASSETS` 並提升 `VERSION`。完整規則見 [09 §新增一個釣點](09-recipes.md#新增一個釣點--一次要生出一整套)。

### 對外 API

```js
px.sprite(f)                                  // → 1:1 的 canvas（有快取）
px.spriteEl(f, scale)                         // → 放大好的 canvas，直接塞 DOM
px.drawSprite(ctx, f, x, y, scale, flip)      // 畫到任意 ctx，以 (x,y) 為中心，flip 水平翻轉
                                              // ★ 精靈天生朝右，flip=true 才是朝左（見下方警告）
```

> ⚠️ **精靈是朝右畫的。** `buildFish()` 的 `x1 = x0 + bodyW` 是頭部，所以頭永遠在 x 大的那一端。`flip` 做的是 `ctx.scale(-1, 1)`，**打開之後才是朝左**。要讓魚「頭朝著移動方向」就得寫 `flip = 速度 < 0`——接反不會報錯，只會整缸魚倒著游（踩過一次，見 [11 §30](11-invariants-and-gotchas.md#30-精靈是朝右畫的flip--朝左)，那裡附了不靠肉眼的驗證腳本）。

雜物（有 `junkArt` 欄位）走 `buildJunk()`，把字元圖置中放進同樣 96×56 的畫布，這樣圖鑑和結果卡不用分兩種排版。

`ostracon` 的重點是**不規則的多邊形輪廓**（規則的方形會被讀成木板或磚，一定要缺角）加上上面幾行橫向刻痕。

後來加的四張各自有一條「不做就認不出來」的規則：`coins` 要**堆疊**（單獨一枚圓片會被讀成瓶蓋或鈕扣，三枚錯開、每枚露出側面厚度才是硬幣）；`shell` 要有**放射狀殼肋 ＋ 偏心殼頂**（少了殼肋就是一個半圓，會跟浮球混在一起）；`flask` 的**瓶頸要比瓶身窄一半以上**（等寬圓筒會被讀成鐵罐），凹陷只做右側；`brimstone` 要有**平的切面 ＋ 明顯稜線**（左上受光、右下陰影），沒有稜線的一團黃色只會被讀成海綿或麵包。

> **「破損要不對稱」這條規則已經用過四次了**（`porcelain`、`shield`、`ostracon`、`flask`）。畫新的破損類雜物直接照做，不要再從對稱開始試。

`porthole` 卡的是**一側凸出來的鉸鏈與蝶形螺栓**——少了它們，一個同心圓會被讀成硬幣或圓盾（`shield` 就是靠中央凸飾才分得出來）；破損照慣例做不對稱（裂縫從右上斜切下來、右下角的玻璃整塊不見）。

後來的三張各自也只卡在一件事：`driftwood` 要有**斷面的年輪**（棍子跟漂流木的唯一差別，所以成本全花在左端那幾圈同心弧上）；`coralfrag` 要**至少分岔兩次**（一根是骨頭、兩根是樹枝、三根以上才是珊瑚）；`dripstone` 要有**斷口的同心層理**（沒有的話跟一根石筍或木樁分不出來），破損照慣例做不對稱。

> **同類的通則**：雜物美術的辨識幾乎都卡在**一個結構特徵**上（貝殼的肋、水壺的頸、硬幣的疊、骨頭的肋排、圓盾的凸飾、漂流木的年輪、珊瑚的分岔、鐘乳石的層理）。畫之前先問「拿掉哪一樣就認不出來了」，把成本花在那一樣上，其餘可以很潦草。

新增一種雜物美術：在 `JUNK_MAPS` 加一筆（`pal` + `map`），然後在 `data.js` 的魚陣列裡用 `junkArt: '新key'`。**不用改 `buildJunk()`**。

## 三 · 釣點場景

`px.drawScene(g, loc, st)`，畫布 **200×340**。

### 船、釣手與狗的待機序列圖

正式資產是 `assets/characters/fishing-idle.png`：一張 1344×64 RGBA PNG，水平排十二格，每格 112×64、每 100ms 換一格（10 FPS、1.2 秒循環）。每格包含同一艘低船身木船、坐姿小釣手與船首的狗；可見範圍約落在場景 x 53～147、y 214～254，仍在 [11 §10](11-invariants-and-gotchas.md#10-場景-canvas-是-object-fit-cover) 的中央安全區，也恢復接近舊程序化船的視覺份量。

船、人、狗先各自產成單一母版，再以固定圖層位置組合十二格；動畫只用 ±1px 的船身浮動、人物呼吸與狗狗抬頭／側移。這個流程刻意避免逐格 AI 產圖：逐格重畫即使提示詞相同，也會讓船舷長度、人物比例或狗的輪廓漂移，幀數提高後反而更像閃爍。色盤採低飽和湖水與深木色、輪廓不使用純黑，追求的是與目前場景協調的原創舒適像素感，而不是複製參考遊戲的角色或船型。

合成順序最後會把前景船殼重新蓋在坐姿釣手下半身前方，只讓彎曲的腿留在船艙暗部，不讓腳跨到外側船舷。這層遮擋十二格共用同一段船殼像素並跟著 `boatOffsetY` 位移，否則腳部會因人物呼吸重新露出，或船身紋理在格與格之間跳動。

`drawBoat()` 第一次執行時用共用 `loadImage()` 非同步解碼；成功後下一幀自然改畫序列圖，載入期間或失敗時改呼叫 `drawBoatFallback()`，用 `ANGLER`＋`DOG` 字元圖和原本的程序化船維持可玩。請勿在每一幀重複註冊 `loadImage()` callback，所以另有 `fishingIdleRequested` 保證只請求一次。

序列圖**不含釣竿、釣線、浮標、倒影與愛心**。這些仍由 canvas 畫，才能跟浮標的拋物線與下沉位置連動。每格人物的手勢略有位移，因此 `FISHING_IDLE.rodAnchor[]` 必須與格數一對一；倒影則讀同長度的 `boatOffsetY[]`，只同步烘進序列的 1px 起伏，不再疊加連續正弦晃動。換圖或重裁時要重新量握竿位置。船身使用資產自己的深木配色，不再讀各釣點的 `scene.boat*` 色票；這是用跨釣點換色換取一致且清楚的木板、馬達與角色細節。

### 分層

```
靜態（有快取；scene.art.background 或 buildBackground → bgCache[loc.id]）
  ├ 天空漸層（loc.scene.sky 陣列逐段內插）
  ├ ★ 地形 above()（依 loc.scene.terrain 分派，見下）
  ├ 岸線
  ├ 水面底色（waterTop → waterBot 分 5 段）
  ├ 地形倒影（把地平線以上 48 列取出、只留較暗的像素、加抖動、疊回水面）
  ├ 深水區塊（waterDeep 疊 35% 透明度）
  └ ★ 地形 below()（選用，浮冰／鳥居／發光浮游生物）

逐幀
  ├ drawSparkle()   水面反光橫線（190 條，位置由 seed 固定，隨時間左右漂移）
  ├ drawBoat()      十二格木船／坐姿釣手／狗待機序列＋愛心＋倒影（缺圖時程序化備援）
  ├ drawRodAndLine()
  ├ drawFloat()     浮標（依 floatSink 下沉）
  ├ 漣漪（st.ripple）
  └ 躍出水面的魚（st.jump）
```

**背景一定要快取**：樹林要畫 230 棵、倒影要跑 `getImageData`，每幀重算會掉幀。`bgCache` 以 `loc.id` 為 key。改了 `loc.scene` 的顏色或 `terrain` 後**必須重新整理**才看得到（同 [精靈快取](#快取) 的問題）。

### 選用的點陣場景底圖 · `scene.art`

`loc.scene.art` 可以提供 `background`、`thumbnail` 與選用的 `horizon`。目前二十個釣點都使用此欄位：主圖 `200×340`，縮圖 `76×50`。

載入刻意是**非阻塞且有雙重備援**：`getBg()` 第一次仍同步建立程序化背景，同時用 `loadImage()` 解碼 PNG；圖片成功後覆寫同一個 `bgCache[loc.id]`，下一個動畫幀自然換圖。載入失敗則保留程序化背景並只寫一筆 console warning。縮圖也先回傳程序化 canvas，圖片完成後覆寫同一張 canvas，因此不必讓 `main.js › boot()` 變成 async，也不會因一張壞圖讓 `file://` 或離線啟動卡住。

點陣背景**只替換靜態層**。`drawScene()` 後面的水面反光、角色序列、狗的愛心、釣竿／釣線、浮標、漣漪、躍魚與 DOM cut-in 全部照舊。主圖不得把這些東西預先畫進去，否則會出現兩艘船或兩個浮標。每張圖的中下方船位必須保留為連續、不透明的水面；海床、珊瑚、沙洲、岩石與碼頭只能留在遠景或兩側，否則動態船會像停在陸地或水底。

`art.horizon` 是圖片水線的位置，跟程序化備援用的 `scene.horizon` 分開。產圖的水線若沒有對準這個比例，`drawSparkle()` 會把反光畫到岸上。主圖與縮圖比例差三倍以上，所以縮圖使用獨立資產，不直接裁主圖；這沿用原本 `locThumb()` 不把 200×340 場景硬縮成 76×50 的設計理由。

場景資產的完整操作步驟見 [09 §替換一個釣點的點陣背景](09-recipes.md#替換一個釣點的點陣背景)。

### 為什麼倒影用 getImageData

一開始想直接重畫一次樹林，但要對齊很麻煩。改成把已經畫好的地平線上方逐列取出、判斷亮度（`lum > 150` 就丟棄，只留暗色剪影）、乘上偏藍的係數、加水平抖動後疊回去。

這個做法在加入地形系統之後**回報更高了**：倒影不知道也不需要知道上面畫的是樹林、崖壁、冰川還是五重塔，它只是把像素往下鏡射。**所以新增一種地形完全不用寫倒影碼。**

## 三之二 · 地形系統 · `TERRAIN`

早期五個釣點共用同一套「遠山＋三層樹林」，只換調色盤——結果就是**每個釣點看起來都一樣，只是顏色不同**。地形系統就是為了解決這件事。

`loc.scene.terrain` 指定要用哪一種，`buildBackground()` 分派：

```js
const terrain = TERRAIN[P.terrain] || TERRAIN.forest;   // 沒指定就退回森林
terrain.above(T);        // 畫地平線以上
...共用的水面、倒影、深水...
if (terrain.below) terrain.below(T);   // 選用：畫在水面上的東西
```

| `reef` | 琉璃珊瑚 | 低平的環礁沙洲 + 碎浪線，水下是一座座礁丘、長在丘上的珊瑚與挖進丘裡的礁洞 | **側視的立體水下結構**（不是俯視的底面）＋ **一條碎浪線把水面切成兩種水色**，見下 |
| `cavern` | 鐘乳暗穴 | **整片洞頂**（沒有天空）+ 倒垂的鐘乳石 + 中央遠處一個拱形洞口，水面被兩側岩壁壓成窄帶 | **唯一沒有天空的地形**＋**倒吊的尖錐**，見下 |
| `wreck` | 曉日沉港 | **一顆壓在地平線上的巨大日盤** + 逆光的港區剪影（倉庫、門式起重機、導標塔）+ 一艘擱淺的貨輪，船身**跨過水線**延伸到水下，水面是一片碎光與一串蛸壺 | **地平線上的天體**＋**同一個物件跨越水線**，見下 |
| `keep` | 朱楓天守 | 天守、層疊石垣、朱橋、楓林與護城河 | **建築壓住山稜的階梯式城郭**；朱橋把遠岸與近水連成一條斜向人造動線 |
| `rotenburo` | 雪見狐湯 | 積雪山林、露天湯、暖色旅館、鳥居、狐像與水面蒸氣 | **冷暖雙光源**＋前景蒸氣遮罩；不是火山湖，而是有人維護的泡湯空間 |
| `wuxia` | 劍影寒潭 | 削直峭壁、橫向棧道、孤瀑、竹影與山巔小亭 | **兩側峭壁上的人造水平棧道**；用一筆筆直人造線把它與自然峽灣分開 |
| `dunhuang` | 敦煌月泉 | 鳴沙丘、規則窟龕、月泉與跨越天空的飛天長綾 | **窟龕蜂巢＋天空長曲線**；沙丘只承載主題，不重複黃沙冥河的金字塔軸 |

#### `pond` 的兩個設計決定

**一 · 人造感全部來自「線是直的」，不是來自畫了什麼。** 自然界不會出現等距、等寬、完全水平或完全垂直的東西，所以只要出現就一定被讀成人造物。這個地形把四件事疊在一起：割草機的等寬條紋、**等距等大**的樹籬球（其他地形的植被全是隨機散佈）、完全水平且每 12px 一道接縫的石砌護岸、直角的木棧道。**成本比畫一座建築低得多，辨識度卻更高**——因為它訴諸的是規律而不是造型。

**二 · 它是唯一看得見水底的釣點。** 其他十一個釣點的水都是不透明的，所以「清澈見底」本身就是識別。做法是在**已經畫好的水面上**疊一層淡的池底色（`bed`），越近越實、越遠越淡，再鋪一層帶滅點的磁磚網格（`grout`）。

> **格距一定要隨深度張開**（`step = 7 + t * 26`，縱線 `6 + t * 26`）。等距的格子會被讀成「一張貼在鏡頭上的方格紙」，張開才有往下看的透視。

實測：避開船的水面區域裡有 **2172/6286（35%）** 的像素落在池底色附近；同一段區域在晨霧湖只有 **17/6286（0.3%）**。差兩個數量級，所以「看得見底」不是錯覺。

#### `tidal` 的三個設計決定

**一 · 這是唯一一個「構圖層級」的差別。** 前十一種地形的地平線以下都是一整片水，換的只是水色。這一種把**陸地畫回水面上**：地平線往下約 80px 是裸露的灘地，只在畫面下緣留一條水道。退潮時真的會留下這樣一條深槽，所以船待在那裡是合理的——不需要為它另外解釋。

**二 · 沙紋是最便宜的紋理。** 平行、等距、微彎的波痕，一道亮的稜配一道暗的谷（各 1px）。在沒有光照系統的情況下，這兩條線就撐起了整片灘地的立體感，成本只有 13 條 `sin` 曲線。

**三 · 積水潭要「多而小」。** 每一個都要有一圈濕沙的暗邊——沒有邊的話只是灘上一塊藍色補丁。而且**尺寸放大就會被讀成水道的分支**，灘地本身就不成立了。目前是 17 個、半徑 3～9px。

> **`drawSparkle()` 每幀會在整個水面區域畫反光橫線，包括蓋在灘地上。** 這裡刻意**不修**：濕沙在退潮後本來就會反光，所以那些橫線讀起來是濕沙的光澤而不是 bug。前提是 `highlight` 要選一個在沙上與水上都成立的暖白（目前 `#fbf6ea`）。**新增「把陸地畫進水面」的地形時要記得這件事**——sparkle 是共用的，不能只為某個地形關掉。

### 場景細緻度標準（2026-08-04 起）

> **`waterfall` 是這個標準的參考實作**，其他釣點目前還是舊的細緻度，會陸續跟進。

初版的瀑布場景被打回來重畫，量化之後發現問題**不是解析度**（200×340 跟一般像素風場景圖是同一個量級），而是**資訊密度**：左半岩壁有 74% 的像素只落在兩個色階上，等於一塊平塗。新場景要過三關：

| | 要求 | 量測方式 |
|---|---|---|
| **色階** | 每一層材質展開成**六階明度**，再用 4×4 Bayer 有序抖動補中間調 | 地平線以上的色數 ≥ 600；最大兩個色階的合計佔比 < 60% |
| **植被** | 樹冠框上緣、平台長灌木、少量垂藤 | 綠色像素佔地平線以上 ≥ 15% |
| **光** | 逆光光暈（先畫、被地形蓋掉、只從缺口透出）＋ 寬而淡的斜射光束 | 目視 |

**單顆石頭的三件事**（少一件就會糊成麻點）：上亮下暗的縱向分層、**只有左半**的頂緣高光（整圈都亮會變成球）、底部一道接觸陰影讓它「坐」在後面的岩上。

> ⚠️ **背景有 `bgCache`，一個釣點一輩子只跑一次**，所以細緻度幾乎不花錢——初版的 80 行變成 350 行，幀率完全沒動。**不要為了效能省這裡的筆數。**

#### 規則的圖案不像自然物（重畫時踩到的三個坑）

| 症狀 | 原因 | 對策 |
|---|---|---|
| 落水點像一張**射箭靶紙** | 畫了一圈圈**完整**的同心橢圓 | 改成隨機半徑的**弧段**，每段各自抖動 |
| 瀑布像**白色水管** | 寬度是常數 | 寬度隨高度變化：頂端收窄、往下散開，再疊兩個不同頻率的起伏 |
| 垂藤像**一排綠色的蟲** | 每個平台掛五六條、長度都差不多 | 一個平台一到兩條，長度差距拉到三倍 |

**通則：自然界沒有等距、等寬、完整的同心圓。** 這條跟 `pond` 那邊反過來用是同一件事——那裡刻意用等距直線表達「人造」，所以這裡只要出現規則圖案就會被讀成人工物。

#### `waterfall` 的三個設計決定

**一 · 跟 `cliff` 刻意做成鏡像。** `cliff` 是兩側暗崖夾出中央的亮縫；這裡是整面暗岩被一道亮柱切開。同一個「亮暗對比」的構圖翻過來用，成本為零，而且兩者放在一起不會認錯。岩壁用**水平**層理（`cliff` 是**垂直**節理），這是第二道保險。

**二 · 亮柱必須跟 `yggdrasil` 的樹幹分開，靠三件事。** 兩者都是「一根貫穿畫面的直立物」：

1. **顏色是全畫面最亮的**（實測瀑柱亮度 234 vs 岩壁 62）。
2. **有橫向流束**——每隔幾列一道較暗的橫紋。樹幹是縱向紋理，這一條就把「在流」跟「站著」分開了。
3. **底部有水霧**，樹幹沒有底。

> **細瀑一定要 2px 以上。** 1px 的垂直線在這個尺寸一律被讀成雨絲（冰川裂隙踩過同一個坑）。目前三道瀑布是 24 / 8 / 5px。

**三 · 水霧做成往上擴散的扇形，刻意不用橫帶。** 橫帶是 `karst` 山腰霧帶的招牌，撞上去等於白做一種地形。扇形的做法是從落水點往上逐列加寬（`spread = 15 + k * 1.5`）並讓 alpha 遞減——這也剛好是水花真實的行為。

#### `caldera` 的三個設計決定

**一 · 凹的天際線是最後一種還沒被用掉的天際線形狀。** 前十一種不是起伏（`forest` `desert`）就是往上長的東西（塔峰、樹幹、金字塔、雪山）。**兩側高、中間低**的凹曲線（`h = 11 + pow(d, 1.6) * 54`）直接說明「你站在一個坑裡面」，一行公式就講完，不需要任何細節。

**二 · 火山錐是尖三角的高風險輪廓，靠平頂救回來。** [§16](11-invariants-and-gotchas.md#16-尖三角剪影一律會被讀成針葉樹) 說這個尺寸下尖三角一律被讀成針葉樹。金字塔的解法是「左右明暗分明」，這裡用的是另外兩件事：**把頂削平**（截頭錐＝火口），加上**從平頂接一根往上加寬的煙柱**。針葉樹沒有平頂，更沒有煙。

**三 · 硫磺階地是全畫面唯一貼著岸線的亮色。** 五道帶狀的黃白結晶疊在水線上方，`sin` 讓每一道的高度起伏。它遠亮於倒影的門檻（150），所以水裡不會有它的影子——跟 `karst` 的白牆同一個理由，刻意接受。

> **水面蒸氣要成塊分佈，不能滿版。** 滿版的垂直筆畫是 `yggdrasil` 極光的做法。這裡用 11 團、各自有寬度與高度的汽柱，而且畫在**水面**（極光畫在天空）——位置與分佈兩件事都不同，才不會被看成「水裡也有極光」。

#### `desert` 的三個設計決定

**一 · 金字塔是「尖三角」的高風險輪廓，靠三件事救回來。** [§16](11-invariants-and-gotchas.md#16-尖三角剪影一律會被讀成針葉樹) 說這個尺寸下尖三角一律會被讀成針葉樹。金字塔避開的方法是：

1. **尺寸夠大**（72×44，是針葉樹的四倍）。
2. **垂直中線一分為二，左受光右陰影**——樹沒有這個。實測同一列的亮面／暗面像素數應該對稱（37/32、28/29、23/24、19/19…）。
3. **底邊坐在平坦的沙帶上**，而不是插在起伏的林線裡。

另外每 6 列疊一道稍暗的橫線當層階，讓斜面不是一片死板的平塗。

**二 · 沙丘一定要有「保底沙帶」。** 沙丘是 `sin` 疊半頻 `sin` 畫的（不對稱稜線＝迎風面長、背風面陡），但**波谷的高度會趨近 0**，只靠曲線的話波谷處會露出一條天空色的縫。初版就是這樣，地平線上方多了一條 10px 的假天空。

```js
rect(0, horizon - 17, W, 21, P.midTree);   // 先鋪實心沙帶，再把沙丘畫在上面
```

上緣必須蓋過**遠沙丘的 `baseY`**，否則波谷還是會從遠沙丘與近沙丘之間漏出來。

**三 · 繪製順序就是景深順序。** `遠沙丘 → 金字塔 → 方尖碑 → 近沙丘 → 棕櫚`。近沙丘要**最後**才畫，才能把金字塔與方尖碑的底部遮住；反過來的話那些建築會像浮在沙丘上面。

`below()` 的石柱要有**比柱身寬的柱頭**才讀得出是柱子而不是木樁；紙莎草的基部 `y` 要夠低，因為花序在 `y - h`，設得離岸線太近的話花序會長到地平線**上面**去（初版就是這樣，紙莎草長在沙丘上）。

#### `yggdrasil` 的三個設計決定

**一 · 構圖改成「單一巨物」。** 前六種地形都是「很多個小東西排開」（樹林、崖壁、冰脊、塔峰、海蝕柱）。這一種反過來：一根樹幹佔掉畫面寬度的兩成以上、從水面貫穿到畫面頂端，樹冠與粗枝**刻意畫到畫面外**，用「裝不下」表達尺度。在 200×340 的畫布上，這是最省力也最強的辨識手段——不需要任何細節，光是輪廓就跟其他六種完全不同。

樹幹位置固定在 `tx = 38`（偏左），把中央水道留給船與兩個浮標。樹幹只畫到地平線；水面以下由**倒影**接手（倒影會自動把樹幹往下鏡射，所以看起來就是從水裡長出來的），另外在 `below()` 畫三道拱出水面的樹根。

**二 · 極光是垂直的簾子，不是橫帶。** 做法：先算一條 `sin` 疊 `sin` 的下緣，再從下緣**往上**畫垂直筆畫、alpha 隨高度衰減；每 3px 一道較亮的筆畫，筆畫之間的明暗差就是簾子的褶皺。

**刻意不用橫帶**——那會撞到 `karst` 的山腰霧帶。

> ⚠️ **兩道簾子的 base 要拉開 40px 以上。** 初版只差 30px、高度又設 34/46，兩道完全疊在一起，青綠與紫糊成一團看不出是兩層。改成 `base = horizon - 22 - b*40`、高度 30/34 之後才分開。驗證方式是逐列統計 R/G/B 對「純天空漸層」的偏離量：**紫簾子的區間 B 大於 G，青綠簾子的區間 G 大於 B，中間要有一段接近零的間隙。**

**三 · 符文石要微微傾斜。** 立正的石板看起來像柱子，歪一點（`lean` 0.08～0.2）才像「被人立起來很久了」。刻痕用橫向短線加偶爾一道豎筆，構成「讀不懂但有規律」的字樣——**不要真的去拼北歐字母**，那個尺寸下拼出來也認不出，反而會變成雜點。

#### `karst` 的三個設計決定

**一 · 塔峰的輪廓：垂直側壁 + 半圓頂。** 側壁往上只內收 18%（`half = w*0.5*(0.82 + t*0.18)`），頂部用半圓收頭。這是為了不撞到既有地形——`shrine` 的錐山是「從頂點線性往下張開」，`forest` 的針葉樹是三角形，`night` 的海蝕柱是矮胖矩形，`cliff` 的崖壁貼著畫面邊緣。實測驗證方式是量同一根塔在不同高度的寬度：**前 9 列從 10 迅速張到 25（圓頂），之後 20 列維持 19～25（垂直壁）**。錐形則會一路線性變寬。

**二 · 橫向霧帶才是「中國山水」的來源。** 三條半透明白色橫帶，越靠峰腳越厚越白（霧積在谷底）：

```js
[[0.30, 7, 0.34], [0.52, 6, 0.24], [0.74, 4, 0.15]]   // [峰高比例, 厚度px, 最大不透明度]
```

把峰群橫切成上下數截，遠近立刻分開。**這是全六種地形裡唯一用橫條的**，也是最省成本的辨識手段：只要三次半透明 `fillRect`，比再畫一層山便宜得多。厚度用 `sin` 加權讓帶緣自然淡出，硬邊會變成一條膠帶。

**三 · 月拱橋畫在 `below()`。** 半圓弧是全遊戲唯一的圓弧輪廓，辨識度最高。它必須在 `below()` 才不會被水面／倒影／深水的半透明疊層洗掉。**荷葉要畫在橋之前**，橋才會像實體壓在葉子上；反過來葉子會浮在橋面上。位置固定在 `cx=158`，避開船（x 40～150、y 216～268）與兩個浮標位置。

#### `rapids` 的三個設計決定

**一 · 三條軸全部放在水面，地平線以上刻意低調。** 其他十四種地形的識別幾乎都在天際線；這一種反過來——上面只有兩層卵石堆與赤楊叢，招牌是**整片斜向的流線**、**石頭的尾流**與**前景巨石**。上面再放高聳的東西只會分掉注意力。

卵石堆用**重疊的橢圓群**：§16 的尖三角、`ice` 的寬扁板塊、`karst` 的圓頂柱都不是這個形狀。單顆石頭照「[場景細緻度標準](#場景細緻度標準2026-08-04-起)」的三件事畫（縱向分層、只有左半的頂緣高光、底部接觸陰影）。

> ⚠️ **卵石的明度階要從 `cobble`（淺灰）展開，不要用 `midTree`/`nearTree`。** 那兩個是谷壁色，石頭跟背後的牆同一個色域就等於沒畫——初版整條岸只看得到一片灰帶加幾顆綠球。河床的卵石本來就比岸壁亮，那是它最好認的地方。

**二 · 「石頭浮在半空」是這個投影的結構性問題，要靠水下體積解決。** 這一版的水面是一整片平塗漸層，**沒有任何東西可以讓物件「站」上去**。所以每顆露出水面的石頭都要自己帶著水下的部分：先畫一塊比露出部分寬一半、往下延伸的深色半透明橢圓，再把半沉的圓頂畫在上面。少了那一塊，石頭就是貼在水上的一片剪影。

同一個問題 `reef` 用礁丘解決，`cavern` 用兩側岩壁解決。**新增「水面上有東西」的地形時，第一個要問的就是那個東西站在什麼上面。**

**三 · 石頭要成群，而且尺寸差距要拉開。** 真實的亂石灘是一堆擠在一起再空一段。平均散開會被讀成「湖上的幾座小島」，全部同樣大會被讀成「一串排開的浮標」。目前是 3 個群心、14 顆、半徑 5～19。

> ⚠️ **`drawSparkle()` 每幀會在整個水面畫水平反光橫線**，蓋在斜向流線上。這裡跟 `tidal` 一樣**刻意不修**：白水本來就到處是碎白，那些橫線讀起來是泡沫。sparkle 是共用的，不能只為某個地形關掉。

#### `reef` 的三個設計決定

**一 · 水下是「側視的立體結構」，不是「俯視的底面」。** `pond` 已經佔走「看得見水底」，但它畫的是一張往下看、帶滅點的**平面**（磁磚 + 透視格線）。這裡的礁是**從畫面下緣往上長**的：有高度、有前後遮擋、有樹冠一樣的輪廓，讀起來像一片水下的森林。兩者放在一起不會混。

> ⚠️ **珊瑚必須長在礁丘上，礁洞必須挖在礁丘裡。** 初版把珊瑚跟洞口各自隨機灑在整片水裡，結果每一株都像浮在半空，黑色的洞口更像是畫面上破了幾個洞。問題不在數量也不在顏色，是**沒有地面**。改成「先堆一座丘，再讓那一叢的東西全部坐在同一座丘上」之後整片才站得住——跟 `rapids` 的石頭是同一個病、同一種藥。

**二 · 碎浪線把水面切成兩種水色。** 地平線下方一條白色**破碎**帶（連續的一條會變成一根桿子），上面是外洋的深藍（`waterTop` 刻意壓深），下面是礁湖的亮青。「同一個畫面裡有兩片不同的海」是這個地形獨有的，成本只有一條抖動過的橫帶。

**三 · 高飽和是識別，不是失誤。** 六個珊瑚色全部拉到最滿，這是全遊戲唯一一格。**不要因為「看起來太吵」把它調灰**——調灰之後它會變成另一個潮落礁灘。

> ⚠️ **白沙底那一層的 alpha 上限只能到 0.3 左右。** 初版拉到 0.52，整片礁湖被洗成一種很淡的奶青色，珊瑚的高飽和度全部被吃掉。**在高飽和的場景裡疊半透明的淺色，等於把識別本身洗掉。**

#### `cavern` 的三個設計決定

**一 · 這是唯一一種把天空整片蓋掉的地形。** 前十四種的天際線再怎麼變，上緣一定是天空漸層；這裡上緣是岩，只在中央遠處留一個拱形洞口透光。「畫面被岩石框住」本身就是識別，不需要任何細節去解釋它是洞。

實作上 `loc.scene.sky` 仍然會被引擎畫出來，`above()` 再整片覆蓋、然後在拱口裡重新內插一次漸層。所以**這個釣點的 `sky` 調的其實是「洞口的光」**，不是天空。

**二 · 倒吊的尖錐是安全的。** [§16](11-invariants-and-gotchas.md#16-尖三角剪影一律會被讀成針葉樹) 說這個尺寸下尖三角一律被讀成針葉樹——但那是**站著**的尖三角。從畫面頂端往下垂的沒有這個問題，因為沒有樹是倒著長的。這等於把一條被封死的軸重新打開。

> ⚠️ **鐘乳石要細而尖。** 初版寬度抓 0.16～0.30 倍高、收尖用 `pow(1-k/h, 0.72)`，每一根都又肥又鈍，加上層理的橫紋看起來像**一排包裝好的糖果**。收尖的指數要大於 1（前段收得慢、末段急收），寬度上限砍掉三分之一。長度差距也要拉到三倍以上，等長的一排是柵欄。

**三 · 窄水道靠 `below()` 的兩側岩壁做，不是靠 `above()`。** `cliff` 是地平線**以上**兩側崖壁夾出中央的亮縫；這裡把同一件事搬到水面**以下**——左右各一塊往中間侵入的暗岩（右邊刻意比左邊寬，對稱會變成一條運河）。加上頭頂的岩，四個邊都是石頭，跟 `cliff` 站在一起不會認錯。

洞口漏進來的光在水面拉出一道縱向亮帶，那是全畫面第二亮的東西，也是水面看得見的唯一原因。

> 「[場景細緻度標準](#場景細緻度標準2026-08-04-起)」的**植被那一關對這個地形不適用**（洞裡沒有植物），改用鐘乳石與流石的層理密度達到同樣的資訊密度。色階與光那兩關照舊。

#### `wreck` 的三個設計決定

**一 · 一顆巨大的日盤是最後一條沒人用的「天空」軸。** 前十五種地形的天空一律只有漸層（`night` 與 `yggdrasil` 加了星點與極光，但那是筆畫不是天體）。一顆半徑 34、壓在地平線上的圓盤同時講完三件事：現在是破曉、光從畫面後面來、所以港區全是剪影。**它還讓這個地形變便宜**——逆光的東西不需要固有色，只需要輪廓加一道上緣的邊緣光。

日盤用六階明度往外遞減（中心接近白、邊緣偏橘），再讓**四道橫貫整個天空的雲帶**切過它。雲帶一定要橫貫全寬：只畫在日盤上會被讀成「太陽有條紋」。實測地平線以上有 2,894 種顏色、最大兩階只佔 8.3%，遠超[場景細緻度標準](#場景細緻度標準2026-08-04-起)的門檻，而成本幾乎全在那四道雲帶上。

> ⚠️ **日盤遠亮於倒影的門檻（150），所以它不會有倒影**（同 `karst` 的白牆）。水面那道日照光路因此**必須自己畫**，就在 `below()` 裡。

**二 · 船身是「同一個物件跨越水線」，這是第二條新軸。** `above()` 畫上部構造（甲板、駕駛台、煙囪、前桅、斷掉的吊桿），`below()` 在**同一段 x 範圍**接上水下船身，中間用三樣東西縫起來：水線的船底漆紅（`redlead`，全畫面唯一的高彩度色）、紅帶下面的點狀藤壺帶、以及往下逐漸內收的船腹。

> ⚠️ **水下那一塊的明度必須從水線的亮走到深處的暗。** 初版整塊用 `shade(hull, 0.10 − t·0.5)`，亮度（≈48）跟 `waterTop`（≈44）差不到一階，**整艘船的下半截等於沒畫**——而跨越水線正是這個地形的賣點。現在是 `0.5 − t·1.1`：水線下 8px 處船殼 114 對水 28，深處反過來變成 15 對 44。物理解釋也剛好成立（低角度的陽光只穿得進水面下那一公尺），見 [11 §36](11-invariants-and-gotchas.md)。

甲板線刻意往右上傾（船頭抬起＝擱淺的姿態）。水平的甲板線只會讀成一艘停著的船。駕駛台的窗要畫成**黑的**——逆光建物的開口一律比外殼更暗，畫成亮的會變成一棟有人住的房子。

**三 · 日照光路做成斷開的碎光，不是一條連續亮帶。** `cavern` 的洞口光已經佔走「水面上一道連續的縱向亮帶」，撞上去等於白做。這裡改成從日盤正下方往觀者展開的**橫向短劃**，密度與 alpha 隨著離軸距離與深度遞減——真實的日照海路本來也是一片碎光。實測在避開船與亮船殼的 y186～214 那一段，x 120～160 有 105 個亮像素，其餘每 20px 只有 0～19。

> `drawSparkle()` 每幀會在整個水面畫水平反光橫線，跟這片碎光疊在一起。這裡跟 `tidal` / `rapids` 一樣**刻意不修**——逆光的水面本來就到處是碎白，sparkle 讀起來就是它的一部分。

水面上還有兩樣東西：碼頭剩下的**半沉木樁**（照 [11 §31](11-invariants-and-gotchas.md) 自己帶著水下的深色體積）與船頭外側的**一串蛸壺**。蛸壺是這個釣點在說「這裡抓的是章魚」的地方，壺口一律朝外——那個朝向就是它跟一串珠子的差別。

### `above(T)` / `below(T)` 拿到的上下文

```js
T = { g, P, R, W, H, horizon, rect, forest }
```

- `P` = `loc.scene`；`R` = 以 `loc.seed` 起始的亂數（**同一個釣點每次長一樣**）
- `rect(x, y, w, h, color)` — 已經幫你做好取整
- `T.forest(baseY, height, color, density, accent)` — 針葉林產生器，任何地形都可以叫

**`below()` 在水面、倒影、深水全部畫完之後才跑**，所以它畫的東西不會被那些半透明疊層洗掉。代價是它得自己處理倒影（`shrine` 的鳥居就是自己鏡射的，靠「R 通道明顯大於 B」把朱色挑出來）。

### 兩個踩過的坑

1. **尖三角在這個尺寸下一律會被讀成針葉樹。** 冰脊初版用三角錐畫，成品跟晨霧湖的樹林幾乎分不出來，等於白做。改成「寬 ≫ 高、頂面是平的」的斜面板塊之後才像冰。**新增地形時，先問自己這個輪廓會不會撞到既有地形。**
2. **從高處往下垂的細線會被讀成雨絲。** 冰川的裂隙初版是從頂端往下畫，看起來像下雨。改成從底部往上長、長度縮短就正常了。

### 新增一種地形

1. `pixel.js › TERRAIN` 加一筆 `{ above, below? }`。
2. `data.js` 的釣點 `scene` 加 `terrain: '新key'`，以及該地形需要的自訂色（例如 `shrine` 用 `snow` `pagoda` `torii`，`ice` 用 `floe`，`night` 用 `star` `plankton`）。
3. **`px.locThumb()` 的 `switch (P.terrain)` 也要補一個 case**，否則釣點選單的縮圖會退回預設的樹林，跟場景對不起來。縮圖刻意不共用 `TERRAIN`——尺寸差 3 倍以上，等比縮放的細節會糊掉，簡化版反而好認。
4. 改完**重新整理**（`bgCache`）。

## 四 · 家園房間

`px.drawRoom(g, st)`，畫布 **200×150**，**回傳 `{ tank: {x, y, w, h} }`** 讓呼叫端知道魚缸的範圍。

```js
st = { time, tankLevel, deco, poster }
```

- 牆（直條紋壁紙）、地板（木紋）、窗戶（看得到湖景）
- **掛畫**：`st.poster` 是一張 canvas，由 `screen-home.js` 用 `px.locThumb(loc, 60, 40)` 產生並快取（`_posterLoc` 記錄目前是哪個釣點）
- **魚缸**：尺寸隨 `tankLevel` 成長（`76 + (lv-1)*12` 寬、`52 + (lv-1)*5` 高），內含水色漸層、光紋、底砂、會搖擺的水草、玻璃外框
- 裝飾：`rug` `plant` `trophy` `cat` `neon` `lamp` `shishi` `shellrack` `cascade` `onsen` `sarco` `flybox` `floats` `driplamp` `beacon` `maplebyobu` `foxlantern` `swordscreen` `apsarabanner`，各自是一段 `if (deco.xxx)` 的繪製碼。
  `flybox`（毛鉤標本盒）的重點是盒裡那排毛鉤**顏色與大小都不一樣**——一排同色同大小的小點會被讀成螺絲；
  `floats`（玻璃浮球串）的網繩**一定要裁進圓裡**（每一列只畫該列的弦長），初版直接畫整條橫線與豎線，三顆球全變成方塊；
  `driplamp`（鐘乳石燈）末端**必須週期性落下一滴水**，那是它跟一盞造型奇怪的吊燈唯一的差別；
  `sarco`（彩繪石棺）的識別重點是**頂端的面具臉**（眼＋假鬍）——少了它就只是一塊直立的木板；
  `shishi`（竹添水）靠**傾斜的竹筒 + 底下的承石**，而且**必須會動**（週期性傾倒），靜態的話就是一根斜靠在牆邊的棍子；
  `shellrack`（貝殼標本架）的三層層板上要放**三種不同形狀**的貝（塔螺／扇貝／芋螺），全畫成半圓的話只是三排小丘；
  `cascade`（循環水景）的水柱橫紋要**每幀往下捲**，不然只是兩個盆子中間一條白線；
  `onsen`（檜木泡湯桶）要有**桶箍**（兩道深色橫帶）才讀得出是木桶，桶口的蒸氣是它跟盆栽分開的地方；
  `beacon`（船首航標燈）吊在天花板 x 50～78，靠**菱形玻璃的透鏡格**＋**每隔幾秒掃過房間的扇形光**辨認，那道光不轉的話它只是一盞怪吊燈；
  `swordscreen`（藏劍屏）在地板放一座低矮劍架，以不對稱的兩柄劍和橫木辨識；`apsarabanner`（飛天幡）從天花板垂下，末端長綾隨時間左右飄，呼應敦煌場景的曲線語彙

> **有五件裝飾是「靠動作定義的物件」**（`shishi` `cascade` `onsen` `driplamp` `beacon`）。這類東西的動畫不是加分項而是**識別的必要條件**，因為它們的靜態剪影跟別的家具沒有差別。加同類裝飾時要一併想好它要怎麼動。
